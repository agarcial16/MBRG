## 2026-11-22 — T1.5 The curation file schema (closes FR-592)
Changed: `src/importer/curation.ts` (`parseCuration(bytes, file)`, `usedProperties`, `CURATION_MAX_BYTES`, the `Curation` types), `types.ts` (`CurationError`), `test/importer-curation.test.ts` (28 tests). Ledger: FR-592 to `DONE_028`.
The schema as implemented: required `primary` (text), `columns` {`key` non-empty text, `name` 1..3 texts}, `params` {`side` integer 64..16,384, `margin` 0..0.5, `minPieceSize` integer 1..10,000, `projection` `laea`|`equal-earth`, optional `gapFill` integer 1..10,000}; optional `context` (<= 8 texts), `select` (filters: `{property, eq|in|gte|lte}` with text or integer operands, or `{bbox:[4 numbers], mode:within|intersects}`), `exclude` (texts), `units` (map key -> {name, kind land|sea|exclude, territory, faction}), `territoryBy`/`factionBy` {property, nameProperty?}, `territoryNames` (map of texts), `factions` (<= 9,999 {key, name, color?}), `seas` (<= 1,024 {name, lon, lat finite}), `insets` ({select: filters, at: [integer, integer]}). Unknown members, wrong types and over-length lists are `invalid-curation` with the member path (`""` for the file as a whole); every problem of one file is returned together, unknown members first within their object, then the members in spec order. Key lengths and every meaning check (names, colours, unknown units) are left to the curation stage.
Decisions beyond the plan: a curation over 16 MiB is `source-too-large` (`what: bytes`), the same kind as a source over 256 MiB, checked in `parseCuration` on the byte length and in the CLI through `readBounded(fs, path, label, CURATION_MAX_BYTES)` on `stat`; a filter holds exactly one operator (each extra operator is a problem at its own path) and `in` may be empty; `at` may hold any integers (an inset outside the image is `inset-outside-image` in M2); property names, paths and `name`/`color` texts are only type-checked (only `columns.key` must be non-empty); `usedProperties` also lists the inset filters' properties; the hand-built draft (empty key, `name: []`) fails on `columns.key` and `columns.name` (T1.6 decides the draft's exact bytes).

## 2026-11-22 — T1.8 Selection (closes FR-594)
Changed: `src/importer/select.ts` (`selectUnits(units, curation)` -> `{selected, other}` or `unknown-unit {unit}` / `empty-selection`; `matchesFilter`; `unitExtent`), `test/importer-select.test.ts` (18 tests). Ledger: FR-594 to `DONE_028`.
Semantics: a unit is selected when every `select` filter matches, it is not in `exclude` and its layer kind is not `exclude`; `other` holds the rest in unit order (M2's other-land layer). `eq`/`in`/`gte`/`lte` compare two integers as numbers and two texts by code units; a text and an integer never compare; an absent value never matches. `bbox` uses the extent of every ring of the unit's polygons (`unitExtent`, reusable for the insets of M2), `within` and `intersects` both inclusive of touching edges; a unit without a position matches no box. `unknown-unit` is reported once per key over `exclude` and the `units` keys, before `empty-selection`.
Decision to carry to M2/M3 (not a change): units are formed by key BEFORE selection (FR-593), so a date-ranged collection must use a per-period key (an id), not the country code: if one country appears in two periods under one key, `conflicting-unit-property` fires on `from`/`to` whatever the selection. The 1914-style fixture is proven both ways (unique id: selects by day; shared key: fails). The deployment guide (T3.6) should say so.
