# Spec 003b — Builder and dev map
Status: approved

## Context and goal
Roadmap step 2 is "viewer on a real map". The viewer cannot be judged without a real map at target scale (lesson: 4x4 test maps hid every real bug), so step 2 is split into: 003a map package contracts, **003b builder and dev map** (this spec), 004 viewer and 005 labels and transitions.

This spec defines:
1. The **id image file format** (PNG, lossless, exact values).
2. An offline **map builder** that turns committed public-domain geographic source data (Natural Earth first-level administrative divisions) into a map package as defined in 003a: projection, rasterization, grouping of provinces into territories and of territories into country factions, sea zones, cleanup of tiny pieces, and adjacency derived from pixel contact.
3. A repeatable **extraction step** that produces the committed source data from a local copy of Natural Earth.
4. The committed **dev map**: a map package of western Europe (Spain, Portugal, France, Italy, Germany) built by the builder, reproducible, valid under specs 002 and 003a (land + sea connectivity, islands, multi-territory factions).

Why: a deterministic builder makes the dev map a reviewable, reproducible artifact rather than a hand-edited file; adjacency derived from the same id image the viewer draws can never disagree with it; and a real-scale map is the gate for judging the viewer.

### Scope split (final decision)
The former spec 003 (dev map and map builder) was split by the user's decision (option A) into two specs, with every requirement id unchanged and each id in exactly one spec:
- **003a Map package contracts**: FR-82 to FR-104, FR-106 to FR-110, NFR-15, NFR-18, NFR-19, NFR-22. Implemented and merged first.
- **003b Builder and dev map (this spec)**: FR-105, FR-111 to FR-131, NFR-14, NFR-16, NFR-17, NFR-20, NFR-21, NFR-23.
- FR-105 (PNG file format) is here because only the builder writes the file and only this spec may add a PNG library. The clause "the builder takes no seed or round as input", formerly in FR-83, is now part of FR-112.

### Delivery (user decision)
One spec, delivered in **two pull requests**, each with its tasks as GitHub issues (AGENTS.md: issues when a spec needs several PRs), each on its own `feat/` branch, squash-merged with CI green.
- **PR1, builder pipeline**: FR-105 and FR-111 to FR-126, NFR-14, NFR-20, NFR-23, tested on small hand-made fixtures held in memory (and on temporary directories only for the command, write and preview behaviour of FR-111, FR-123 and FR-126). No Natural Earth data, no dev map. Includes the repository configuration extensions listed below and the first step of NFR-19 completion (the pending set shrinks).

## Users
- **Map author** (developer today): needs to rebuild the dev map from committed sources, see why a build failed, and review the result before the viewer exists.
- **Developer** of the viewer (spec 004): needs a real map at target scale.
- **Spectator / predictor** (indirect): needs recognisable factions (Spanish country names) and territories, and a map whose adjacency matches what is drawn.

## User stories
- US-1. As a developer, I want a real-scale dev map committed in the repository so that the viewer is built and judged against real data from the start.
- US-4. As a map author, I want the builder to be deterministic and to fail with explicit errors (never write a broken or partial package) so that the committed dev map is always valid and reproducible.
- US-5. As a map author, I want a preview image of a build so that I can review grouping, sea zones and islands before the viewer exists.

(US-2 and US-3 are in 003a.)

## Definitions
- Terms defined in 003a are used with the same meaning: **map, map package, id image, pixel coordinates, row-major order, background, 4-adjacent pixels, contact, piece, map unit, presentation data**. Faction, faction order, land territory, sea zone and linked: as in spec 002.
- **Natural Earth fields** are written here in lower case (`adm0_a3`, `adm1_code`, `name`, `name_es`). Some Natural Earth files store them in upper case; the extraction step maps them to these names.
- **Country code**: the Natural Earth `adm0_a3` field (three letters; it is Natural Earth's code, not guaranteed to equal an ISO code).
- **Province code**: the Natural Earth `adm1_code` field of a first-level division.
- **Contact count** between a set of pixels P and an entry B: the number of pairs of 4-adjacent pixels with one pixel in P and the other of value B.
- **Source province**: one feature of the geographic source data (Natural Earth 1:10m first-level administrative division), identified by its province code and belonging to the country of its `adm0_a3`.
- **Country record**: the properties (no geometry) of a selected country's Natural Earth admin-0 feature: `adm0_a3`, `name`, `name_es`.
- **Selected country**: a country, identified by its country code, declared in the grouping table; its provinces become land territories of the map.
- **Excluded province**: a source province of a selected country that the grouping table marks as not part of the map (far-away parts, FR-113).
- **Other land**: the admin-0 outlines of countries that are not selected, plus every excluded province. Other land is never water.
- **Grouping table**: committed builder input that declares the selected countries (each with an optional preferred colour), lists the territories (each with a unique text key, its country, its source provinces and an optional name; never a colour), and lists the excluded provinces.
- **Present** (for a name taken from an input): an own field whose value is a non-empty text value. Absent fields, null, the empty text and non-text values are not present.
- **Sea zone seed**: a named point (longitude, latitude) of the committed sea zone source; each seed produces one sea zone (FR-116). Seed names are Spanish.
- **Water pixel**: a pixel whose centre lies in no land territory and in no other land (FR-115).
- **Frame**: the square of projected coordinates that is mapped onto the W × H id image (FR-114).
- **Minimum piece size (S)**: the smallest number of pixels a piece may have in a built id image (FR-117).
- **Library**: third-party code added as a dependency of the repository (constitution rule 1). Runtime built-in modules are not libraries.
- **Runtime**: the Node.js version selected by the repository's `.nvmrc` file (present today, holding `24`; the CI workflow takes its Node version from it), on any operating system.
- **Extraction box**: a fixed longitude/latitude rectangle committed as a parameter of the extraction step, defined independently of the builder frame (FR-131).

## Functional requirements

### Id image file
- FR-105: THE SYSTEM SHALL store the id image as a PNG file that is lossless, 8-bit-per-channel RGB truecolour without alpha and without palette, non-interlaced, and made only of the chunks `IHDR`, one or more consecutive `IDAT` and `IEND`, in that order, so that every reader gets the exact stored values; the channels carry the values of 003a FR-106. WHEN the builder reads a PNG (the round trip of FR-122, the committed image in FR-130), IF the file has any chunk other than exactly `IHDR`, one or more consecutive `IDAT` and `IEND` (for example `PLTE`, `tRNS`, `gAMA`, `cHRM`, `sRGB`, `iCCP`, `cICP`, `tIME`, `tEXt`, `zTXt`, `iTXt`), a bit depth other than 8, a colour type other than RGB truecolour, or interlacing, THEN it SHALL reject the file with `invalid-png` and return no pixel values. A malformed file (wrong signature, chunk CRC mismatch, truncated data, data after `IEND`, a decompression failure, decompressed data of the wrong length, an unknown row filter type, or a width or height of 0) is likewise rejected with `invalid-png`. The chunk and malformation checks run before any pixel decoding.

### Builder: inputs and source data
- FR-111: THE SYSTEM SHALL provide an offline map builder, run by one command, that reads only local committed input files, never accesses the network, and produces a map package. Fetching source data at build time or at viewer runtime is not supported.
- FR-112: THE SYSTEM SHALL take as builder input: the source province geometry of the selected countries; the country records of the selected countries; the other-land geometry (admin-0 outlines of non-selected countries); the grouping table (which declares the selected countries); the sea zone seeds; the source metadata record holding the Natural Earth version (FR-131); and the build parameters (side W, with H = W; margin; S). These inputs SHALL fully determine the output, and the builder SHALL take no seed, round, match state or round record as input (003a FR-83). IF an input is malformed (unreadable or not valid JSON, a value of the wrong shape or type, W not an integer of at least 1, margin not a finite number of at least 0, S not an integer of at least 1, a non-numeric or non-finite coordinate, a sea zone seed without a text name), THEN THE SYSTEM SHALL fail the build before any other check with one `invalid-input` error (`reason`: English text naming the input and the problem) per malformed input, in the order of the inputs listed in this requirement.
- FR-113: IF the grouping table has any of the following problems, THEN THE SYSTEM SHALL fail the build and report one error per problem, with these kinds and data fields, ordered by kind in the order of this table and, within a kind, by the code-unit order of the value of the first data field:

  | Kind (`kind`) | Data fields | Condition |
  |---|---|---|
  | `duplicate-country` | `country` | A country code declared more than once as a selected country (one error per repeated code). |
  | `unknown-country` | `country` | A selected country with no country record in the source data. |
  | `duplicate-territory-key` | `territory` | A territory key used by more than one territory (one error per repeated key). |
  | `invalid-territory-country` | `territory` | A territory with no country, or whose country is not a selected country. |
  | `territory-color` | `territory` | A territory with a preferred colour (preferred colours exist only for factions, 003a FR-86, FR-99). |
  | `empty-territory` | `territory` | A territory that lists no source province. |
  | `missing-territory-name` | `territory` | A territory made of two or more source provinces with no present name. |
  | `unknown-province` | `province` | A province code listed in a territory or in the excluded list that is not the province code of a source province of a selected country. |
  | `duplicate-province-assignment` | `province` | A source province listed more than once in total over all territories and the excluded list (one error per province). |
  | `province-country-mismatch` | `province`, `territory` | A source province listed in a territory whose country (valid, not `invalid-territory-country`) differs from the province's `adm0_a3`. |
  | `unassigned-province` | `province` | A source province of a selected country listed in no territory and not excluded. |
  | `empty-country` | `country` | A selected country with no non-excluded source province. |

  `country` holds a country code, `province` a province code and `territory` a grouping-table key. Every problem is reported; none blocks the others. Each error is reported once per distinct value of its data fields (for example, an unknown province code listed twice gives one `unknown-province`, and two territories sharing a key that both have a colour give one `territory-color`). Within a kind, errors with the same first data field value are ordered by the code-unit order of the second (`territory` in `province-country-mismatch`).
- FR-114: THE SYSTEM SHALL project longitude and latitude (degrees, treated as coordinates on a sphere) with the Lambert azimuthal equal-area projection, north up, centred on the point whose longitude is the midpoint of the longitude range and whose latitude is the midpoint of the latitude range of all vertices of the non-excluded source provinces. Polygons are projected vertex by vertex, and their edges are straight segments in projected coordinates. The frame SHALL be the bounding box, in projected coordinates, of the projected vertices of the non-excluded source provinces, expanded symmetrically along its shorter side into a square, then expanded on each of its four sides by the margin times the square's side. The frame SHALL be mapped onto W × W pixels, each pixel covering an equal square of the frame, with x growing east and y growing south: a projected point (X, Y) has continuous pixel coordinates u = (X − frame west edge) / pixel side and v = (frame north edge − Y) / pixel side; it lies inside the frame if and only if 0 ≤ u < W and 0 ≤ v < W, and then lies in pixel (⌊u⌋, ⌊v⌋); the centre of pixel (x, y) is the point with u = x + 0.5, v = y + 0.5. A point exactly on the edge between two pixels therefore lies in the pixel to its east or south.
- FR-115: THE SYSTEM SHALL assign each pixel by its centre point only (never by partial coverage, never blending values): to the land territory whose non-excluded source provinces contain the centre; IF several territories contain it, THEN to the first of them in map order; ELSE, if other land contains it, to background; ELSE the pixel is a water pixel and is handled by FR-116. Containment SHALL be:
  1. a feature (one or several polygons) contains a point if any of its polygons contains it; overlapping polygons of one feature form a union and never cancel each other;
  2. a polygon contains a point if its outer ring contains it and no hole contains it strictly inside; a point on the boundary of the outer ring or of a hole counts as contained by the polygon; overlapping holes each remove their interior;
  3. a ring contains a point if the point lies on the ring's boundary or the even-odd rule (crossing count) puts it inside; ring orientation (winding direction) has no effect;
  4. consecutive equal vertices count as one vertex (collapsing them changes no point set and is not simplification);
  5. a ring with zero area (fewer than three distinct vertices after rule 4, or a shoelace area of exactly zero on its source coordinates), for example one created by rounding, is ignored: as an outer ring its polygon contains nothing (not even its boundary); as a hole it removes nothing.
- FR-116: THE SYSTEM SHALL create one sea zone per sea zone seed and assign each water pixel to the seed whose pixel (the pixel in which the projected seed point lies, FR-114, including a point on a pixel edge) is reachable from it by the fewest 4-adjacent steps through water pixels only; ties go to the seed listed first. Water pixels from which no seed pixel is reachable (lakes, inland gaps) SHALL become background. IF the seed list is empty, a seed point lies outside the frame, a seed's pixel is not a water pixel, or two or more seeds share a pixel, THEN THE SYSTEM SHALL fail the build reporting, in this kind order and then by the position of the (first) seed named: `no-sea-seeds` (no data field); `seed-outside-frame` and `seed-not-water` (`seed`: 0-based position in the seed list, `name`); `duplicate-seed-pixel` (`seeds`: positions, ascending; `x`, `y`: the shared pixel).
- FR-117: WHEN all pixels have been assigned, THE SYSTEM SHALL repeat the following until no piece has fewer than S pixels: take the piece with fewest pixels among pieces with fewer than S pixels (ties: the piece whose first pixel in row-major order comes first), reassign all its pixels to one target, then recompute the pieces. Only entries with a contact count of 1 or more with the piece are candidates in any step; a step whose candidates all have contact count 0 has no candidate and falls through to the next step. The target of a land territory's piece SHALL be: (1) the other land territory of the same faction with the highest contact count with the piece; else (2) the land territory of any faction with the highest contact count; else (3) the sea zone with the highest contact count; else (4) background. The target of a sea zone's piece SHALL be the other sea zone with the highest contact count, else background. Ties between targets go to the first entry in map order. IF a reassignment would leave a map entry with no pixel, THEN THE SYSTEM SHALL fail the build with `vanished-entry` (`territory`: the entry's id), stopping at the first such reassignment. Background pixels are never reassigned. An implementation MAY use an incremental algorithm instead of recomputing all pieces after each reassignment, provided its result is identical to this loop; identity SHALL be verified by tests comparing it with a direct implementation of this loop on fixtures that include ties, cascades (a reassignment that makes another piece smaller than S or merges pieces) and every target step for land and sea.
- FR-118: WHEN the pixel assignment is final, THE SYSTEM SHALL derive every link of the map from contact in the id image (003a FR-108), with no link added or removed by hand, and SHALL write each entry's neighbor list in ascending map order.
- FR-119: THE SYSTEM SHALL create exactly one faction per selected country and make it the owner of every land territory of that country; sea zones have no owner (002 FR-57).
- FR-120: THE SYSTEM SHALL order and number deterministically: factions in code-unit order of their country code (`adm0_a3`), numbered 1 to K in that order; land territories grouped by faction in faction order and, within a faction, in code-unit order of their grouping-table key; sea zones after all land territories, in the order of the sea zone seeds; territory ids 1 to N in that map order. As a result faction order equals faction id order.
- FR-121: THE SYSTEM SHALL write the presentation data with factions in faction order and territories in map order; faction names from the country record's `name_es` when present, otherwise its `name` when present (the grouping table has no faction name and cannot override a source faction name); land territory names from the grouping table when present, otherwise, for a territory made of one source province, from that province's `name_es` when present, otherwise its `name` when present; sea zone names from the sea zone seeds (Spanish map data, 003a NFR-18); preferred faction colours only where the grouping table gives them for a selected country. An entry for which no name is present gets no `name` field. The builder SHALL never normalize, trim or otherwise change a name taken from its inputs, and SHALL never fall back to another source because a present name is invalid; IF a resulting name is missing or not valid (003a FR-87), THEN the build SHALL fail through FR-122 (`invalid-name`) rather than repair it.

### Builder: output, failures and review
- FR-122: WHEN a build has produced its outputs in memory, THE SYSTEM SHALL run map validation, the presentation check (003a FR-91) and the id image check (003a FR-109) on them, and SHALL verify that the encoded id image decodes back (FR-105 reading) to the same pixel values; IF any error is found, THEN it SHALL report every error and fail: the map validation errors once (when the map is invalid, the other two checks add nothing), otherwise the presentation errors, then the id image errors, then `png-round-trip-mismatch` (no data field) when the decoded values differ.
- FR-123: IF a build fails for any reason, THEN THE SYSTEM SHALL exit with a failure status and SHALL create, modify or delete none of the three package artifacts. WHEN a preview was requested (FR-126) and the failure happens after rasterization (FR-115), THE SYSTEM SHALL still write the preview of the last pixel assignment it computed, outside the package, as a review aid. A successful build SHALL replace the three artifacts by first writing all three as temporary files in the target directory and then renaming each over its target; IF writing any temporary file fails, THEN it SHALL remove the temporary files it wrote, leave the previous artifacts byte-identical and fail with `write-failed` (`artifact`: `map`, `presentation` or `image`); IF the first rename fails (no artifact replaced), THEN it SHALL remove all temporary files, leave the previous artifacts byte-identical and fail with `write-failed` (`artifact`: the artifact of that rename); IF a rename fails after another rename succeeded, THEN it SHALL remove the temporary files not renamed and fail with `partial-write` (`replaced`, `notReplaced`: lists of artifact names in the order `map`, `presentation`, `image`). IF a requested preview (FR-126) cannot be written, THEN the build SHALL fail with exit status 1, leave the three package artifacts untouched and print one JSON error line of kind `preview-write-failed` (`preview`: the preview path); this also applies when the build had already failed (the build errors are printed as well, and the status stays 1). Verified by tests on temporary directories with injected write and rename failures.
- FR-124: WHEN a build succeeds, THE SYSTEM SHALL print a deterministic build report listing: the source data version (from the source metadata record, NFR-21); W, H, the projection centre and the frame; the number of factions, land territories and sea zones; the size of the smallest piece in the final id image (after FR-117); every reassigned piece (former entry, pixel count, new entry or background); every excluded source province; and every map entry with more than one piece. Report field labels are English.
- FR-125: THE SYSTEM SHALL write the map and the presentation data as JSON text with this fixed formatting: two-space indentation with every object field and every list element on its own line, empty lists written `[]`; keys in this order: map `territories`; land entry `id`, `owner`, `neighbors` (no `kind` field: an absent kind means land, 002); sea zone `id`, `kind` (`"sea"`), `neighbors`; presentation `factions`, `territories`; faction `id`, `name`, then `color` only when given; territory `id`, `name`; numbers as plain integers; non-ASCII characters written as raw UTF-8, never as `\u` escapes; UTF-8 without byte order mark, LF line endings and a final newline. These JSON bytes SHALL be identical for identical inputs on the runtime (Definitions) on any operating system. THE SYSTEM SHALL produce an id image whose decoded pixel values are identical for identical inputs on the runtime on any operating system with the locked library versions, and whose bytes are identical for two builds in the same environment. Verified in CI, on the runtime only, by a build-twice byte comparison of all three artifacts on a test fixture (not on the dev map) and by the rebuild test (FR-130); and by a test that the `.nvmrc` file exists and holds one version and that the CI workflow takes its Node version from it.
- FR-126: WHEN asked, THE SYSTEM SHALL also write a preview image, outside the map package, in which each faction has its preferred colour when given and otherwise a colour distinct from every other faction's, sea zones share one colour and background another, all these base colours being pairwise distinct; every pixel with a 4-adjacent pixel of a different value is drawn darker, meaning each of its three 8-bit channels is ⌊c / 2⌋ of its base colour channel c, and every other pixel is drawn in exactly its base colour. IF the requested preview path is the package directory or lies inside it, THEN THE SYSTEM SHALL exit with status 2 before reading or writing anything, print one JSON error line of kind `usage-error` (`reason`: `preview-inside-package`, `preview`: the preview path) and create, modify or delete nothing. The preview SHALL never be committed: its default location is outside the package directory and matched by the repository ignore rules, verified by a test.

### Dev map
- FR-127: THE SYSTEM SHALL include in the repository a committed dev map package built by the builder from committed inputs, with: selected countries Germany, Spain, France, Italy and Portugal (factions 1 `DEU`, 2 `ESP`, 3 `FRA`, 4 `ITA`, 5 `PRT` by country code, FR-120); one land territory per first-level region, grouped in the grouping table: Germany 16 states, Spain 16 autonomous communities (all except the Canary Islands; Ceuta and Melilla excluded), France 13 metropolitan regions, Italy 20 regions, Portugal 5 mainland regions (Norte, Centro, Lisboa, Alentejo, Algarve), **exactly 70 land territories** (16 + 16 + 13 + 20 + 5, confirmed by the user and checked by a test); between 10 and 20 named sea zones; W = H = 2048; margin 2%; S = 40; and no preferred colour for any faction.
- FR-128: THE SYSTEM SHALL keep the committed dev map package valid: the map passes map validation with no error (including land + sea connectivity, 002 FR-71), the presentation data passes the presentation check, the id image passes the id image check, and the committed PNG meets FR-105 (read without `invalid-png`).
- FR-129: THE SYSTEM SHALL make the dev map exercise spec 002, asserted on the committed map: at least one land territory linked to no other land territory and to at least one sea zone (island); at least one faction whose land territories are not all connected through its own land; at least one land territory linked to no sea zone (landlocked); at least one sea zone touched by 2 or more factions; at least one sea zone linked to another sea zone.
- FR-130: WHEN the test suite runs, THE SYSTEM SHALL rebuild the dev map from the committed inputs and verify that the map and presentation data are byte-identical to the committed ones and that the id image decodes to the same pixel values as the committed one. The rebuild runs inside the normal test suite with an explicit per-test timeout above the NFR-16 build threshold.
- FR-131: THE SYSTEM SHALL provide a repeatable extraction step, run by one command on a local copy of the Natural Earth 1:10m files given by the developer and without network access, that produces the committed source data from the grouping table's selected countries and the extraction box (Definitions):
  1. every first-level division of the selected countries, wherever it lies (so that FR-113 can check the grouping table), with only the properties `adm1_code`, `adm0_a3`, `name`, `name_es`;
  2. the country records of the selected countries, properties only (`adm0_a3`, `name`, `name_es`), no geometry;
  3. from the admin-0 outlines of non-selected countries, each polygon whose own bounding box intersects the extraction box (decided per polygon, not per country), with only the property `adm0_a3`;
  4. a source metadata record holding the Natural Earth version, read from the version text file shipped with each Natural Earth dataset used (one per dataset: first-level divisions and admin-0 countries), compared after removing trailing line breaks; IF that text is missing for a dataset used or differs between the datasets used, THEN the extraction SHALL fail with `invalid-source-version` (`files`: the version text file names, code-unit order).

  Removing the space or NUL padding (trailing space and NUL characters) of fixed-width DBF text values when reading them is decoding, not a trim of names in the sense of FR-121. Features and kept polygons SHALL be kept whole (never clipped to the box); clipping to the box is allowed only if the whole-feature output exceeds the 10 MB limit of NFR-17, and then the provenance note states it. The step SHALL never simplify geometry; it MAY only round every coordinate to the same fixed number of decimal places, at least 4, so that vertices shared by two polygons stay identical, and collapse consecutive vertices made equal by that rounding (FR-115 rule 4). Running it twice on the same files SHALL produce byte-identical output. The extraction box SHALL cover the dev map frame: every pixel centre of the outermost rows and columns of the dev map frame, converted back to longitude and latitude, lies inside the box (asserted on the committed data). Because Natural Earth itself is not committed, the automated test runs the extraction on a small synthetic fixture in the Natural Earth file format and checks selection, kept properties, whole features, rounding, collapsing, the metadata record, the `invalid-source-version` failure and byte-identical output on two runs; reproducing the committed source data from the real Natural Earth files is a manual done criterion.

## Non-functional requirements
- NFR-14 (Builder purity): every builder step between reading the inputs and writing the outputs is deterministic and performs no file, network, clock or system-randomness access; it can be run from in-memory inputs to in-memory outputs, without files. The only runtime built-in module it may use is `node:zlib`, and only its synchronous in-memory deflate and inflate functions (PNG encoding and decoding); this exemption is documented in the source scan. PNG encoding and decoding by an approved PNG library (NFR-20) is called through an adapter outside the scanned core source and passed to the in-memory build; that library may use runtime built-in modules internally but performs no file, network, clock or randomness access, which the throwing-clock test covers. Verified by: a test that runs the in-memory build of a small fixture while the clock and system randomness are replaced by functions that throw (this also covers library code called by those steps); a source scan of the builder's own core source for I/O, clock and randomness APIs and for imports of runtime built-in modules; a test that the scan's exemption list is exactly those two `node:zlib` functions; and tests that planted synthetic sources importing another built-in module (e.g. `node:fs`) or using another `node:zlib` function are flagged.
- NFR-16 (Performance at real scale): in the CI test run, one full dev map build (from reading the committed inputs to the three artifacts written) completes in under 60 seconds, and map validation plus presentation check plus id image check of the dev map complete together in under 1 second. The plan SHALL measure both times (on the PR1 pipeline or a prototype at 2048 × 2048) and either confirm these thresholds or propose others for the user's approval through a change of this spec. The rebuild stays in the normal test suite with an explicit test timeout (FR-130), so a slow build fails on the timing assertion, not on the runner's default timeout.
- NFR-17 (Repository size): the committed id image is at most 2 MB, the committed map and presentation data at most 500 KB together, and the committed source data (all outputs of the extraction step) at most 10 MB. Verified by a test on the committed files.
- NFR-20 (Libraries: scope and pinning): libraries may be added only for the four areas of the Compatibility section (map projection, PNG reading/writing, rasterization/geometry, reading Natural Earth shapefile/DBF), each only after the user's approval of its justification in the plan; the first three are used only by the builder and the extraction step, the fourth only by the extraction step; the build tooling exception of the Compatibility section (a TypeScript launcher, the runtime's type declarations, and type declarations of an approved library) is allowed as development dependencies of the builder workspace only, each also approved by the user; the pure shared and sim packages keep no third-party dependency (a dependency on another workspace of this repository is not a library) and import none of them, and the viewer neither depends on nor bundles them unless a later spec says so; each is pinned to an exact version in the package manifest (no version range) and in the lockfile; each has a licence compatible with the repository's MIT licence (MIT, ISC, BSD-2/3-Clause, Apache-2.0 or public domain), re-checked on npm at install time and recorded in the plan. Verified by a test that reads the manifests and checks: the builder workspace's dependencies are exactly the approved list with exact versions; the shared and sim packages have no third-party dependency; no source of shared, sim or the viewer (when it exists) imports an approved library. The approved list grows in PR2 with the approved shapefile/DBF library.
- NFR-21 (Provenance and licence): the committed source data is accompanied by a provenance note stating the source (Natural Earth), its version, the source files used, the extraction box, the trimming, rounding and collapsing applied (and clipping, if FR-131 needed it), the extraction command, the approximation of Portugal's regions from whole districts, and the licence (public domain, credited as "Made with Natural Earth"). Verified by a test that the note exists and contains the version string of the committed source metadata record, which is also the version the build report prints (FR-124).
- NFR-23 (Library behaviour): any library used by the builder or the extraction step SHALL: give the same result on every run with the locked version (no clock, randomness, network, locale- or thread-count-dependent output); never alter pixel values (no colour management, gamma, premultiplied alpha, palette quantisation or lossy step); in rasterization, assign each whole pixel to exactly one value by its centre point (FR-115), with no antialiasing or coverage blending; and leave the core transformations (projection, rasterization, sea zones, piece reassignment, adjacency, and PNG encoding, which uses only the `node:zlib` exemption of NFR-14 besides any approved PNG library) callable on in-memory data (NFR-14). Verified by: the build-twice byte comparison (FR-125) and, in PR2, the rebuild test (FR-130); the throwing clock/randomness test (NFR-14); rasterization tests with pixel centres exactly on edges, on shared vertices and inside holes, asserting no pixel holds a value outside the input ids; and an in-memory encode/decode round trip with values using all three channels (including 1, 255, 256, 65,535, 65,536 and 16,777,215) plus a chunk check (FR-105).

## Edge cases
- A pixel centre exactly on the border shared by two provinces of different territories: contained by both (FR-115), so it goes to the first in map order; it is never lost to water.
- A province ring with clockwise orientation, or a hole wound the same way as its outer ring: same result (even-odd, FR-115 rule 3). Two overlapping polygons of one feature: union. A ring collapsed to a line or point by rounding: ignored (FR-115 rule 5).
- A seed point exactly on the edge between two pixels: it lies in the pixel to its east (vertical edge) or south (horizontal edge); on the frame's east or south outer edge it is outside the frame (`seed-outside-frame`) (FR-114, FR-116).
- A narrow strait (e.g. Messina, about 3 km, about 3 pixels): it may close at this resolution, linking the island to the mainland by land; the build report and preview make this visible and it is accepted as built (no hand-edited links, FR-118).
- An island whose surrounding water reaches no seed: the water becomes background, the island has no link, and the build fails with `disconnected-map` naming it (FR-122).
- An island territory with several pieces (e.g. Balearic Islands): one territory with several pieces, linked to the sea zones its pieces touch. An islet smaller than S with no other territory touching it becomes part of the touching sea zone (FR-117 step 3).
- A small piece touching only background and a same-faction territory through a corner: no candidate has contact (corners are not contact), every step falls through, and it becomes background (FR-117).
- A territory so small that no pixel centre falls in it, or all of whose pieces are below S with nothing it can keep: the build fails naming it (`missing-territory-pixels` through FR-122, or `vanished-entry`, FR-117); the author must regroup it in the grouping table.
- Small far islands of non-excluded provinces (e.g. Lampedusa, Pantelleria, Heligoland) are part of their province, widen the frame (FR-114) and must lie inside the extraction box; this is a known, accepted effect.
- Excluded provinces inside the frame: **Ceuta and Melilla** (Spain, on the North African coast) fall inside the frame and become other land, hence background, never sea. Excluded provinces outside the frame (Canary Islands, Azores, Madeira, French overseas regions): no effect; they also do not widen the frame (FR-114).
- A source province of a selected country not listed in the grouping table: `unassigned-province` (FR-113), even if it lies outside the frame.
- A province listed in a German territory but whose `adm0_a3` is `FRA`: `province-country-mismatch`. A territory listed with an empty province list: `empty-territory`. Two territories with the key `bayern`: `duplicate-territory-key`. A selected country with no country record: `unknown-country`. A colour given on a territory: `territory-color` (FR-113).
- A country record whose `name_es` is the empty text or null: the faction is named from `name`. A `name_es` with a trailing space: used as given, so the build fails with `invalid-name` (no fallback, no trimming, FR-121). Neither present: no `name` field, `invalid-name` (FR-121, FR-122).
- Small exclave surrounded by another selected country (e.g. Llívia, Spain, inside France) and smaller than S: goes to the touching land territory with the highest contact count (FR-117 step 2), since no territory of its own country touches it. If it has S pixels or more, it stays a second piece of its territory and links it to the surrounding territory.
- Small exclave surrounded by other land (e.g. Büsingen, Germany, inside Switzerland) and smaller than S: becomes background (FR-117 step 4).
- Microstates (Andorra, Monaco, San Marino, Vatican, Liechtenstein) and non-selected neighbours (e.g. Switzerland, Austria, Benelux, the United Kingdom, North Africa): other land, hence background; an enclaved microstate is a background hole; a hole smaller than S stays background (FR-117 never reassigns background).
- Gaps or overlaps between source provinces, or between selected provinces and other-land outlines (different source layers): overlaps go to the land territory (FR-115); a gap wider than a pixel becomes water, which becomes background when no seed is reachable (FR-116) and may remove a contact, which the build report and preview make visible.
- A sea zone that ends up with no pixels: the build fails with `vanished-entry` (FR-117).
- A seed placed on land, on other land, outside the frame or on the same pixel as another seed: the build fails (FR-116).
- Two seeds in the same water body: the body is split between them by step distance (FR-116); a seed in a water body cut off from the open sea (e.g. a lagoon) produces a zone that may not touch the rest, which is valid if map validation passes.
- A landlocked land territory (e.g. Madrid) or a landlocked faction (none in the dev map): valid; its links are land only. FR-129 asserts at least one landlocked territory.
- **Portugal's 5 regions are grouped from whole districts**: they only approximate the official regions where those borders do not follow districts; the grouping table and the provenance note (NFR-21) state the approximation.
- Building twice in a row from the same inputs in one environment: byte-identical outputs (FR-125). Building on another operating system with the runtime and the same locked versions: identical JSON bytes and identical decoded pixels; PNG bytes may differ, which FR-130 tolerates by comparing decoded pixels. Byte-identity is tested in CI on the runtime only.
- A failed build after a successful one: the previously committed package is left byte-identical (FR-123); a requested preview is still written if the failure came after rasterization.
- A rename failing after the map was already replaced: `partial-write` names `map` as replaced and `presentation`, `image` as not replaced, and the build fails (FR-123).
- A PNG with a palette, alpha, 16-bit channels, interlacing, or any chunk other than `IHDR`, `IDAT`, `IEND` (e.g. `gAMA`, `sRGB`, `iCCP`, `cICP`, `cHRM`, `tIME`, a text chunk): `invalid-png` when read; the builder never writes one and FR-128 rejects it for the committed dev map.
- Natural Earth files whose version texts disagree, or a file without one: `invalid-source-version` (FR-131).
- An other-land country that is very large or has a long coastline (e.g. Norway) and intersects the extraction box: each of its polygons whose bounding box intersects the box is kept whole, the others are dropped; a country spanning the antimeridian (e.g. the United States, Russia) contributes only its polygons near the box (e.g. Kaliningrad); clipping is allowed only if the whole-feature output exceeds 10 MB (FR-131, NFR-17).
- A candidate library that antialiases, applies colour management by default, depends on native binaries that differ per platform, or cannot be pinned exactly: it can only be proposed if the plan shows how each NFR-23 constraint is met (e.g. an option that disables the behaviour) and a test proves it; otherwise own code is used for that area. The plan must justify each proposed library against determinism, size (install and repository), maintenance (release activity, open issues), licence (NFR-20) and the ability to assign whole pixels by centre, and name the alternative discarded.

## Out of scope
- The presentation data format, the id image value contract and their checks (003a); this spec only uses them.
- All rendering: viewer, camera, colours on screen, borders, labels, transitions (specs 004, 005). The preview image (FR-126) is a review aid only.
- Other importers (flat-colour PNG, Azgaar) and any map editor.
- Fetching source data at build time or at runtime; any map other than the dev map.
- Insets or non-contiguous frames (e.g. the Canary Islands in a box).
- Hand-edited links or hand-edited pixels in the committed package.
- Changes to the map format, presentation data format, map validation, `MatchState`, `RoundRecord` or the sim; new exports of the shared package.
- Libraries outside the four allowed areas (except the build tooling exception of the Compatibility section, builder workspace only), and any library in the pure packages or the viewer.
- Running the extraction on real Natural Earth files in CI.
- Server, Discord bot, predictions.
