## 3. Data model: schema v2 (FR-390, FR-391)
`SCHEMA_VERSION = 2`; `SCHEMA_V1` is kept verbatim and run first (idempotent); the new statements are `SCHEMA_V2_ADDITIONS`.
| Table | Columns | Notes |
|---|---|---|
| `lobbies` | `match_id` PK -> matches, `public` INTEGER (0/1), `expires_ms` INTEGER, `started_ms` INTEGER NULL, `expired_ms` INTEGER NULL | one row for every match created through the public path; operator matches have none. Indexes: `(public, started_ms, expired_ms)` for the counts. |
| `players` | `match_id`, `player_id`, `name`, `name_key`, `token_digest`, `joined_seq` (the `seq` of its `player-joined` event = join order), `joined_ms`; PK `(match_id, player_id)`; UNIQUE `(match_id, name_key)`; INDEX `(token_digest)` | `player_id` is the namespaced id `player:<local>`. Holds digest only. |
- `open`: `user_version` 0 creates v1+v2 in one transaction; 1 runs the additions and sets 2 in one transaction; 2 opens; other values refused (`unknown-schema-version`). A v2 file opened by an 008 server is refused by that server (accepted; no downgrade).
- `meta.schema_version` is updated with `user_version` (both asserted by `store-open`).
- Counts: open lobbies = `lobbies.public = 1 AND started_ms IS NULL AND expired_ms IS NULL`; running public = `lobbies.public = 1` joined to `matches.stage IN (phase-1, phase-2, locked)`; `runningCount()` (008, operator limit) keeps counting every running match? **Q4**.
- Memo: scope for public creation `{credentialDigest: digest('public:'+source), match: null}`; join `{digest('join:'+source), match}`; start `{host token digest, match}` (as advance).
- Storage check (NFR-47 (d) extended): the lobby rows hold nothing about a round; `storedFutureViolations` unchanged and re-run over lobby matches.

## 5. Identity (FR-377 to FR-382)
- `ids.ts`: `PLAYER_TOKEN_BYTES = 32` (256 bits, 43 base64url characters, in the 22-256 credential set so `readBearer` accepts it unchanged); `newPlayerToken(random)`, `newPlayerLocalId(random)` (9 bytes).
- `identity.ts`: `Identity` gains `{role:'player', digest, playerId, matchId}`; `playerIdentity(identity, found)` mirrors `hostIdentity`; `submitterOf(identity, body.playerId)` replaces `playerIdFor` for the two prediction routes: client -> as 008; player -> the token's own id or `forbidden`. `limitKeys` gains `case 'player'`: `${class}:${digest}` with the client limits, so each token has its own budget and a shared NAT does not throttle a lobby.
- Join (service, one transaction): memo check -> match exists -> stage check (`lobby`, `phase-*`, `locked`; `match-finished`, `match-halted`, `match-expired`) -> cap (`match-full`) -> name rule (shape errors come before `name-taken`) -> draw id and token (draws only after nothing can fail) -> `insertPlayer` -> `appendEvents(player-joined)` -> `updateMatch(lastSeq)` -> memo -> commit -> publish. A unique-index violation on `name_key` inside the transaction is mapped to `name-taken` (a concurrent join cannot double-book a name).
- FR-380: a player joining a running match has no rows for earlier phases; scoring already iterates stored predictions, so no code is needed beyond the join stage check; tested.
- FR-382: no route to read, change or recover a token; `join` is the only place a token leaves the server.

## 6. Forced absorber (FR-387 to FR-389) — amends 008 scoring
- `steps.ts` `closePhase1`: `forced = candidates.length === 1`; the `PublicVictim` carries `forced: true`; `anchors` come from `forcedAnchors(...)` when forced (Q2). `apply()`: the `ScoredPhase` `absorber` is omitted when `view.victim.candidates.length === 1` (no row is written, `persist` already skips an empty row set). The winner phase is unchanged.
- `predictions.ts` `decideSubmission`: for kind `absorber` in stage `phase-2` with one candidate -> `forced-absorber` (after `prediction-closed`, before `invalid-choice`). Phase-1 absorber submissions stay `prediction-closed`.
- `scoring.ts`: `ScoredPhase` is unchanged in shape; a test pins "d = 1 never scores" at the core and the service. `isScored` and `scoredPhaseCount` count the absorber phase of a forced round as scored-and-empty (generation arithmetic unchanged: 2N, +1 for a revealed victim).
- Public data: `PublicVictim.forced`, `victim-revealed` event; `results` event for a forced round's phase 2 is still emitted (empty), as for any empty phase (008 G2).
- Anchors: `forcedAnchors(anchors, timing, forcedSeconds, instant, cause)` pure; stored through the same `updateMatch`; restart recovers it from `c1_ms/c2_ms/a_ms` (nothing new to store). Manual timing: no anchors, nothing to shorten (FR-388 last sentence).
- Order in M1 (before the lobby): the change touches 008 goldens, so it lands alone and its re-pin is reviewable.

## 7. Lobby, start, expiry (FR-371 to FR-376)
- `core/lobby.ts` (pure): `joinDecision(view, count, max)`, `startDecision(view, now, timing)` -> new view (`phase-1`, anchors from `now`, `lastStepMs = now`) and the `schedule` event, `expireDecision(view, now)`. `stage` checks reuse the `Stage` type; `nextStep(view)` is `null` for `lobby`/`expired` (no step, no clock).
- `start` under `manual` timing: stage `phase-1`, no anchors; the host then advances as in 008 (FR-375).
- Scheduler: a lobby has the expiry wake-up only; `armAt` is generalised to take a kind (`step` | `expiry`); the 008 step wake-ups are untouched. `start()` (service) enumerates lobbies and re-arms (a restarted lobby is still a lobby; one already past its expiry expires at once, late, with the effective instant).
- Stream: the hub is unchanged; a late subscriber replays from the stored events (including `player-joined`, FR-376).

## 8. Limits and abuse (FR-370, FR-381, NFR-72)
- Settings (all new, read like the existing ones, names only in problems): see section 14.1 for the list and the proposed defaults (Q8).
- Order inside the public creation decision: shape (`readCreation`) -> map in public list (`unknown-map` for an unlisted map: same as an unknown map, nothing disclosed) -> bounds (`invalid-timing` items by rule) -> caps (`too-many-matches`) -> draw -> store. A refusal creates and stores nothing and draws no random bytes (008 pattern).
- Rate keys are added through `ticket.extend` after the body is read (so a malformed body is `invalid-request` before it costs a creation slot); a refusal cancels the stage-1 ticket (counted nowhere).
- Bodies stay bound by the 4,096-byte rule; lists by 500 per page; names by 24; players by `maxPlayers`; memo rows by the rates; streams by the existing gauge (anonymous 5 per address).
- Memo growth: creation/join/start rows live 24 h; the purge timer already covers them. Test: N joins at the rate limit leave at most N memo rows, purged at 24 h + 1 ms.

## 9. Test strategy (Vitest only, titles start with the ids)
- Pure: `names` (accents, case, spaces, length 24/25, code points, empty, control chars, homoglyph note), lobby decisions, `forcedAnchors` (fake clock values: L at below/equal/above F; L2 = 0), source/proxy parsing, identity roles, protocol encoders/decoders/cursors.

- HTTP (real listener, port 0, fake clock): every route with and without credentials, impersonation, limits at their edge, CORS on the new paths, headers, `Retry-After`.
- Secrecy: twin lobbies (same public data, different secret) give byte-identical lobby reads/streams; the winners/players reads expose no wrong guess, no unscored phase (FR-386); the 008 secrecy suites pass unchanged.
- Goldens: 008 goldens re-pinned in M1 only (section 12); a new `apps/server/test/golden/dev-lobby.json` (hand-derived lobby, join order, names, forced rounds) with an independent generator (own arithmetic; imports nothing from `core/lobby.ts`/`core/scoring.ts`), M5.

## 13. Risks
- **Secrecy.** (a) Lobby: the secret is drawn at creation; nothing derived may be public (commitment is, as in 008). Twin-lobby test and storage scan. (b) `forced` is derived from `candidates` already public from the reveal: it reveals nothing before the phase-1 close. (c) The winners read could leak an unscored phase or a wrong guess: it reuses `isScored` and `results.correct = 1` only; mutation proofs on both. (d) `playerCount`/names are public by design (D5); a name is attacker text: JSON strings only, bounded, never in a log line except length + hash.
- **Determinism.** No sim change; forced anchors and expiry take `now`/`instant` as parameters; ids and tokens from the injected random source; names normalised by pure code (`String.prototype.normalize` is locale-free; `toLowerCase()` not `toLocaleLowerCase`).
- **Persistence/restart.** v1 -> v2 open in one transaction (a kill mid-open leaves v1); join/start/expire are single transactions with their events; the expiry wake-up is re-armed from `lobbies.expires_ms` at `start()`; kill-point tests with `failWrite` cover join, start, expire and creation. A v2 file cannot be reopened by an 008 build (accepted; no downgrade path).
- **Abuse.** Anonymous creation is the new attack surface: bounded by caps, rates (per source and overall), the 24 h expiry, the player cap and memo purge. Residual: many sources (botnet) up to the overall limit; a public `manual` match never ends if its host leaves (Q9); `X-Forwarded-For` spoofing if hops are mis-set (default 0); name homoglyphs/impersonation of another player's name (out of scope: no filtering); player-token loss is permanent by design (FR-382).
- **008 goldens that change and why**: section 12; the only cause is the forced absorber (d = 1 never scores, shorter phase 2, `forced` mark). Lobby/identity changes add tables, stages and optional fields and change no 008 golden by construction (pinned by M5 byte tests).
- **Cross-package.** Widening `Stage` breaks `apps/web` typecheck (Q7). `apps/web` readers of events refuse unknown types: a web client subscribed to a lobby match before spec 013 will treat `player-joined` as a protocol fault; acceptable because no 013 UI exists, but note it for the PR.
- **Size.** M3 and M4 are the largest (each ~2,400 estimated); checkpoint stops at 1.5x per task as in 008.

## 15. Questions for the user (nothing below was guessed; tasks marked "blocked on Q#" wait)
- **Q1** FR-371 says "a created match starts in `lobby`", FR-369 says the operator path "is unchanged". Do operator-created matches start in `lobby` or immediately in `phase-1` as in 008? Plan: immediately (NFR-75 and every 008 suite keep passing); the alternative rewrites every service test and golden.
- **Q2** FR-388 shortens "phase 2 ... min(L2, F) instead of L2". In 008, phase 2 (absorber window) lasts L1 and L2 is the `locked` interval. (a) Which interval is shortened? F = 5 equals the public minimum L2 (5), so shortening L2 would never act in public matches; shortening L1 (public minimum 10) would. (b) Does A move earlier (round shorter) or stay (longer `locked`)? "The next round's anchors do not move" admits both. Plan assumes nothing; the pure `forcedAnchors` and its tests wait for the answer (M1 T3).
- **Q3** Namespace of web players: plan proposes reserved `player` (ids `player:<12 chars>`); `web` collides with 48 test sites that configure a client `web`.
- **Q4** Does the 008 operator running-match limit (`MBRG_MAX_RUNNING_MATCHES`) also count public matches? Plan: yes, it counts every running match; the public cap is an additional, lower one.
- **Q5** NFR-73 says only digests are stored, FR-381 returns the token again on a repeated join. Plan: the 24 h memo keeps the plain token (as FR-238 does for the host token), then deletes it. Confirm, or accept that a lost reply loses the player.
- **Q6** Lobby events: plan stores `schedule` (stage `lobby`) at creation and `schedule` (stage `expired`) at expiry, no new event types. Confirm, or specify.
- **Q7** Widening `Stage` breaks `apps/web` typecheck and `live-text.test.ts`. May M2 touch `apps/web` minimally (two table entries, two strings, one test) although the interface is spec 013? Alternative: no `lobby`/`expired` stage value on the wire (not what the spec says).
- **Q8** Defaults not in the spec (caps, rates, maximum public interval) in 14.1 marked *; and which windows: the limiter window is fixed at 60 s.
- **Q9** May a public match use timing `manual`? A public manual match never ends if its host leaves and holds a running slot. Plan: refuse `manual` in public creation (`invalid-timing`) unless told otherwise.
- **Q10** The closed error codes for `start` on a started or expired match are not named: plan uses new `match-started` and `match-expired`.
- **Q11** CORS: public `POST` create/join carry no `Authorization`; plan applies the allowed-origins rule to them (a foreign page cannot create or join), while GET reads stay `*`. Confirm.
- **Q13** FR-370 limits "running public matches". Is the cap checked at creation (counting lobbies that may start later), at `start` (refusing the start with `too-many-matches`, lobby kept), or both? Plan: open lobbies are capped at creation; the running-public cap is enforced at `start` only if the user says so (otherwise it is unreachable, since lobbies are what start).
