# Plan 022 — Display names for client players
Spec: `spec.md` (approved 2026-11-17; OQ1 to OQ4 as proposed; the name is the member display name in the Discord server). Tier: Full SDD. Status: draft, awaiting the user's approval of plan and tasks in this chat. Written against the code at `main` (7ff2c20); every claim of section 2 was read in the code on 2026-11-17.

## 1. Shape of the change
A client player has no `players` row and no `player-joined`; the server only stores its predictions under `discord:<id>`. The change adds **one optional member `name` to the submission body** and **one table `client_names (match_id, player_id, name)`** written in the transaction of the accepted prediction. The three reads that show names (leaderboard rows, phase winners, own-player read; plus the phase results rows, section 5) look the name up, **but only for a player id that already has a `results` row** (scored). Nothing in the simulation, the map format, `MatchState`, the draws, the events, the roster or `GET /players` changes (NFR-114, FR-534).

Discarded: writing a `players` row for client players (it would list them in `GET /players`, the lobby and `player-joined` before scoring: 008 P12, FR-534; and it would add a name key, so `name-taken`, FR-532). Discarded: a `name` column on `predictions` (touches the table of every golden and every scoring query; a name per prediction instead of per player; the table of results/rank would carry names). Discarded: names per namespace across matches (OQ1, needs retention and its own privacy review). Discarded: widening the name rule for client names (OQ2): the bot cleans, the server keeps the one rule `readName`.

## 2. Findings verified in the code (2026-11-17)
- `readSubmission` (`packages/protocol/src/read.ts:106`) refuses unknown members through `firstUnknown(o, SUBMISSION_FIELDS)` (`wire.ts:58`): a `name` is `invalid-request` today. `readName` (`names.ts:35`) is the rule and also the decoder of `LeaderboardRow.name?` (`decode.ts:102`), so a client name that passes the rule decodes in every reader.
- The submit route reads the body three times (`http/server.ts` shape, authorize, playerLimit) through `readSubmission`; they need no edit. `service.submit` (`service/matches.ts:1339`) runs the policy of 018 before the memo, then `decideSubmission`, then `putPrediction`; the body digest is `sha256(canonicalBody(...))` of the raw body, so a body without `name` keeps its digest and a body with it differs (FR-530).
- Names reach the reads through the single funnel `store.playerNames(matchId, ids)` (`sqlite.ts:562`), called from `phaseResults` (1559), `playerResults` (1600) and `leaderboard` (1615); the winners read does not use it: `winnersAfter` is an **inner join** on `players` (`sqlite.ts:187`), so a client player is left out.
- **Finding that shapes the design (not in the spec text):** `playerResults` answers for ANY well-formed player id, scored or not. If the name lookup keyed only on `client_names`, `GET .../players/discord:<id>/results` would return a name for a member who predicted but is not scored yet, which reveals that they predicted (NFR-112, 008 P12). The lookup therefore requires a `results` row for the same player in the same match (section 3). The leaderboard, the winners and the phase results are built from `results` rows, so for them the condition is already true.
- Phase results rows are a fourth place that carries `name` today (the spec lists three reads). Decision PD2 below.
- The bot sends the submission in one place, `io/handler.ts:46` (`client.submit(...)`), body built in `io/server-client.ts:96`; the interaction user is read in one place, `discord/shell.ts:129` (`Who = { channelId, userId }`). The bot sends no `requestId` on submissions, so a changed name never meets the memo (FR-539).
- Schema is at version 3 (`SCHEMA_VERSION = 3`, `schema.ts:8`); `purgeExpired` deletes child tables first from a list (`sqlite.ts:514`); `TABLES` is the list the table scan uses.
- The viewer already shows `row.name ?? localName(playerId)` in `board-model.ts`, `results-model.ts` and `play-view.ts`; FR-538 needs a check, expected without source changes.

## 4. Persistence (FR-536, NFR-113)
`SCHEMA_V4_ADDITIONS` is one statement: `CREATE TABLE IF NOT EXISTS client_names (match_id TEXT NOT NULL REFERENCES matches (id), player_id TEXT NOT NULL, name TEXT NOT NULL, PRIMARY KEY (match_id, player_id))`. No name key, no unique index (FR-532). `openStore`: `user_version` 0 creates v1..v4; 1 adds v2..v4; 2 adds v3 and v4; 3 adds v4; each inside the same transaction as the version change. The upgrade writes no row of any existing table, `meta` included (the 018 rule: `meta.schema_version` is write-only; a new file gets 4, an upgraded one keeps its old value); 4 opens as is; 5 is `unknown-schema-version`, so a 018 server (supports 3) refuses a v4 file by its existing rule. `TABLES` gains `client_names`. The writer is `putClientName(matchId, playerId, name)`: needs a transaction, an existing match, a client player id (`<namespace>:<local>`, not `player:`), a non-empty name of at most 24 code points; it inserts or, when the row exists, replaces the name (`INSERT ... ON CONFLICT (match_id, player_id) DO UPDATE SET name`): this is the one `UPDATE` of the table (latest accepted name wins, FR-531, FR-539). The only `DELETE` is in `purgeExpired`: `client_names` joins the child-first list before `matches`, so the name lives and dies with its match (FR-536, NFR-113; without it the foreign key would fail the purge transaction and the memo purge with it).

**Scored-only reads.** `clientNames(matchId, ids)` returns the names of the ids that have a `results` row in the match: `SELECT c.player_id, c.name FROM client_names c WHERE c.match_id = ? AND c.player_id IN (...) AND EXISTS (SELECT 1 FROM results r WHERE r.match_id = c.match_id AND r.player_id = c.player_id)`. `winnersAfter` becomes `FROM results r LEFT JOIN players p ... LEFT JOIN client_names c ON c.match_id = r.match_id AND c.player_id = r.player_id` selecting `COALESCE(p.name, c.name)` and requiring it not null (a client without a name stays left out, as today; a match with no client names returns the same rows and bytes). `results` has no index on the player (its key is match, round, kind, player): the lookup scans the rows of one match, as `playerResultsAfter` and `leaderboardTotals` already do; the schema of existing tables is not touched (no new index).

## 5. Pure decisions (`core/client-name.ts`, parameters only; NFR-116)
```
Caller = {role:'client', namespace} | {role:'player'}
submissionName(caller, name: string | undefined):
  name === undefined                       -> {action:'none'}
  caller.role === 'player'                 -> {action:'refuse', error: invalid-request ['name']}   // PD1
  otherwise                                -> {action:'store', name}
withClientNames(playerNames, clientNames)  -> a new map: playerNames first, then client names for ids not present
                                              (the two id spaces do not meet: `player:` is reserved, 011)
```
Service `submit`, inside the transaction, after the 018 policy and BEFORE the memo lookup: `submissionName` (a refusal is `invalid-request` naming `name`; nothing is written, memoised or drawn). After `decideSubmission` returns ok (a changed prediction, a new one or an identical resubmission): `putPrediction` when it has something to store, then `putClientName` when the action is `store`, in that order, in the same transaction (FR-531). A refused submission (`prediction-closed`, `forbidden`, `unknown-match`, a memoised refusal) writes no name. A memo replay returns the first reply and writes nothing: its content digest includes `name`, so the same `requestId` with another name is `request-id-reused` (the bot sends none). Duplicates are allowed: no `nameKeyTaken`, no `name-taken` (FR-532).

Reads: `phaseResults`, `playerResults` and `leaderboard` call one helper `namesOf(matchId, ids)` = `withClientNames(store.playerNames(...), store.clientNames(...))`, then the existing `nameOf` member rule (present only when known, FR-533). `phaseWinners` needs no change in the service.

**PD2 (decision for the user's approval).** The spec lists three reads; `phaseResults` also carries `name` today and the winners of a phase are a subset of its rows, so leaving client names out there would show a name in one read and the id in the other for the same row. Proposed: include it (four read functions; the NFR-112 source scan allow-lists exactly those four callers of `clientNames` and the one query of `winnersAfter`). The wording "three reads" of NFR-112 is read as "the reads of FR-533". Alternative: exclude phase results (the viewer would show ids there).

**PD1 (decision for the user's approval).** The spec is silent on a `name` sent by a player token (open match). Proposed: `invalid-request` naming `name` (a player already has its join name; refusing is clearer than ignoring, and nothing is stored). A client credential sending `name` on an open match stores it like on a client-only one (FR-531; it shows only where the id shows).

## 6. Bot (FR-537, NFR-116)
`cleanDisplayName(text: string): string | undefined`, pure: NFC; replace every code point outside `[\p{L}\p{N} _.-]` with a space (so an emoji between words does not glue them); collapse runs of spaces to one; trim spaces; cut to 24 code points (not UTF-16 units); trim spaces again (a cut can end on one); empty: `undefined`. The output always passes `readName` (a test runs it over a corpus and over random strings through the real `readName`). `shell.ts` builds `displayName` from the interaction (`member.displayName`, i.e. nickname, else global display name, else username; fallback `user.displayName`, then `user.username`) in a tiny pure helper over a plain object so it is tested without Discord; `Who` gains `displayName`; `handler.submit` sends `name: cleanDisplayName(...)` when defined, on every prediction (OQ3). A server that refuses `name` (older server, `invalid-request` naming `name`) is the existing generic error sentence; no retry without `name` (OQ4: bot and server ship together). The name is never logged or put in a state file.

## 7. Test strategy (Vitest; no new library)
- Pure: table tests for the two core functions and for `cleanDisplayName` (examples, edge cases, `readName` acceptance over a corpus). Protocol: `readSubmission` with valid and invalid names (order of the named field), digest of a body without `name` equal to the digest pinned from the code at `main`, key lists.
- Store: upgrade from v1, v2 and v3 files built as `store-upgrade-v3.test.ts` does (v3 fixture made by the 018 path), a hash of every row of every pre-existing table before and after, version 4, version 5 refused, atomic failure; `putClientName` (insert, replace, rollback, shape refusals, fault wrapper counts it, `lobby-durability` write list); `clientNames` returns nothing for an id without results; `winnersAfter` with players, client names and no names; purge with a client-only and an open expired lobby; source scan of `client_names` statements.
- Service and HTTP on a real server (as 018): submit with every caller class and stage, latest name wins, same name twice, duplicate names across members, no `name-taken`, refusal writes nothing, memo cases, limits, reads before and after scoring.
- NFR-112 secrecy: a planted name (a string no other text contains) through a full run: no read, event, stream frame, log line or error before scoring contains it; the probe of `player-results` for an unscored client id answers as for an id that never predicted (byte-identical to an unknown id); after scoring only the four reads carry it; a source scan shows `clientNames(` called only from those four service functions and `client_names` only in the listed statements.
- NFR-114 twin test: same fake random source and same predictions, one run without names and one with: all reads equal except the `name` member of scored rows; the no-name run is byte-identical to a run of the 018 code path (pins); open match unchanged; the 008, 011, 014 and 018 goldens and the protected-path diff at the end of every task.
- Mutation proofs (011 method) for each guard: scored-only condition removed, name written on refusal, `name-taken` applied, upgrade writing a row, purge list without the table, left join turned inner.
- The hand run (done criterion 3) is the user's, after M7.

## 8. Risks
- R1 Persistence upgrade (v1, v2, v3 to v4): mitigation as 018 R1: side table only, hash of every old table before and after on three fixtures, atomic failure test.
- R2 Secrecy of "who predicted": the unscored probe through `player-results` (section 2) and any new read of `client_names`. Mitigation: scored-only query, byte-identical probe test, source scan of the callers (NFR-112).
- R3 Memo and digest: `name` enters the content digest of a submission that carries it; a body without it keeps the old digest (pinned). A bot that later adds a `requestId` and changes its name would get `request-id-reused`: noted, the bot sends none.
- R4 Spec 021 works in parallel in `apps/bot/src/core/announce.ts` and one line of `io/handler.ts`, and may extend the ledger: rebase on `main` before M6 and before the ledger task; keep the handler diff small; the ledger pins (counts) are recomputed from the file at task time, not copied from this plan.
- R5 Write order: the name write follows the prediction write in the same transaction; a failure after the first rolls both back (test with the fault wrapper). Order is pinned like the 008 lesson.
- R6 Name rule vs Discord names: heavy decoration or emoji-only names clean to nothing and show the id (accepted by the spec; the hand run checks it). Accented names pass because the rule allows letters of any script and the bot normalises to NFC; combining marks that do not compose are replaced by a space.
- R7 Size: estimated 1,500 to 2,200 changed lines with tests: one PR into `main` at the end; split per milestone if the branch passes about 3,000.
- R8 Models (AGENTS.md): planner and reviewer of M3, M4 and M5 (persistence and secrecy) run on Opus; implementers and the M1, M2, M6, M7 reviews on Sonnet.
