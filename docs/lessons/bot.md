# Lessons: Discord bot (`apps/bot`)
- A test waiting for an exact post count (`=== N`) is racy: wait for the full deterministic count.
- The countdown comes from the server's schedule anchors (c1/c2 and reportedTime), never from the pace (a forced phase breaks it).
- Discord edits at ~1 per second per message are at the rate-limit edge: one edit in flight, skip a tick.
- The Discord token is typed by the user in their own terminal, never in chat.
- Never drive real Discord from automation (ToS; bots cannot press buttons or run slash commands). Test automation = one start command + a fake Discord at handler level.
- Client-only matches: the bot creates them; the viewer closes their join door (spec 020); the lobby message carries a viewer link (spec 021).
- The e2e harness (spec 023, `test/e2e/`): the plan's outcomes are PINNED (a golden), not recomputed — a change to the dev map, `@mbrg/sim` or the seeds fails the test on purpose and the fixture is re-pinned. `boot()` takes any `{ url }`: the fake server or the real in-process one.
- Spec 024: the bot hashes the guild id in `discord/translate.ts` and nothing else may name a guild (source scan); the `Interaction` holds only the key, and no custom id, log line or state file holds a key, a cursor or a user id.
- A history message keeps its PAGES (not only cursors) in memory per message id: page 1 has no cursor, so asking it again would open a new snapshot; Previous is answered from memory with no request. Paging never extends the 5 minutes (the expiry is fixed at posting).
- Discord fixes the privacy of a reply when it is deferred: a public command that may fail privately (`/mbrg history`) deletes the deferred reply and follows up with an ephemeral sentence.
- The map package has no map name (only factions and territories): the "map name" of a history entry is the map id, as the lobby shows it (`ctx.mapName` is the hook for the day a name exists).
- Spec 025 (ranking): a ranking message keeps its PAGES per message id like the history (own registry `lookupRanking`, ids `mbrg:rk:p|n:<page>`); the order and the key live in the walk, never in an id, and the cursor request must repeat the order (the server refuses a cursor of another order). The accuracy note "Menos de 10 predicciones" opens the first page where unranked rows appear: the embed needs the LAST ROW of the page before (`ctx.previous`, read from the stack), so a page shown again from memory places the note the same way.
- The percent of a row is the floor in integers (`BigInt`): float math drifts at the edge (199/200 is 99 %, never 100 %).
- The e2e harness plays TWO matches of one server (spec 025 FR-572: the same seeds make the same rounds, only the picks differ, `PLAN_B`); the stages count posts from the base the earlier match left. Its pins are worked out by hand from the picks and cross-checked against the public leaderboards of both matches; the ranking is read through the bot (embed) AND straight from the server (`raw`: statistics, ranks, shown names). A pick must be a faction still alive (a round 3 victim pick of an eliminated faction is "not an option now").
