## 2. Architecture (whole spec)
```
@mbrg/shared (pure, unchanged)      @mbrg/sim (pure engine + 3 exports, FR-313)
            \                          /
             @mbrg/protocol (pure, new in M2a): wire types, own-property readers, error kinds and
             their fixed order (FR-301), timing rules (FR-233), canonical forms: map-digest bytes,
             state-digest text, canonical request body (FR-282), cursor format (FR-279)
                     |                                   |
apps/server (new): core/ (pure)          apps/web (existing): live client (M5), pure parts in src/core,
  stage machine, schedule, anchors,        DOM/network in src/ui; debug scene unchanged (FR-309)
  late rule, effective and reported
  time, advance decision, prediction
  validation, scoring, ranking, paging
  shell: clock, random, secret (HMAC), SQLite store, HTTP router, SSE hub, rate limiter, settings
```
- **Pure core, effectful shell.** Every decision is a pure function `decide(view, input, now) -> { writes, events, reply }` over a match view loaded from the store; the shell runs `writes` in one storage transaction, then publishes `events`, then sends `reply` (FR-290, FR-292). Round seeds reach the core through a `roundSeed(k)` function parameter: in production the HMAC of section 5, in tests the test-only source of FR-260, which only `createServer(options)` accepts and `main.ts` never passes.
- **Public view.** Reply and event builders take a `PublicMatch` type that has no field for the secret, round seeds, the pending absorber or the pending state (FR-257, NFR-47(b)); a type-level test pins its keys.
- **One engine.** The core calls `playRoundWithSeed` at the phase-1 close and again at the application (FR-241, FR-243, FR-256); `absorptionCandidatesOf` and `livingFactions` validate predictions and give n and d (FR-262 to FR-264, FR-271, FR-272).

## 5. Secret, commitment and round seeds (FR-252, D5) — fixed once
Published verification rule; it never changes for stored matches. A change would need a new rule name and a spec change.
- **Secret**: 32 bytes from the injected random source (production: `crypto.getRandomValues` of the platform). Published at the end as 64 lowercase hexadecimal characters.
- **Commitment**: SHA-256 of the 32 raw secret bytes, as 64 lowercase hexadecimal characters.
- **Message for round k** (k a whole number from 1 to 2^31 − 1): the ASCII bytes of `mbrg/round-seed/v1/` followed by k in decimal without sign or leading zeros (for example `mbrg/round-seed/v1/1`).
- **Round seed**: `s_k` = the first 4 bytes of HMAC-SHA-256(key = the 32 raw secret bytes, message) read as an unsigned 32-bit big-endian integer.
- Verification (published with the secret, FR-259): recompute the commitment, every `s_k`, then `playRoundWithSeed` from `getState(map, 0, 0)`.
- Test vectors (pinned in T7): secret = bytes 0x00..0x1f; k = 1, 2, 3, 4, 70 and 2^31 − 1; each value computed twice, with `node:crypto` `createHmac` and with the platform's Web Crypto `subtle.sign` in Node, which must agree; plus RFC 4231 test case 2 through the same helper to prove the HMAC primitive.

## 6. The sim exports (FR-313, D6, D21) — M1
- `checkState(map, state)` (internal): `state` is an own-property object with exactly `mode`, `round`, `owners`; `mode === 'classic'`; `round` a whole number 0..T (`-0` as 0); `owners` an array with one `[territoryId, factionId]` pair per land territory of the map, in map order, each pair an own-property array of length 2, each faction a faction of the map. Any failure gives one `invalid-state` error (no detail, like `invalid-seed`).
- `playRoundWithSeed(map, state, roundSeed)`: errors together in this order: map validation errors, `invalid-state`, `invalid-seed`; then `round-out-of-range { round: state.round + 1, total: T }` if `state.round === T` or fewer than 2 living factions; then the internal `playRound` on a normalised copy (input never mutated), which returns `isolated-faction` as today.
- `absorptionCandidatesOf(map, state, faction)`: map validation errors, `invalid-state`, `invalid-faction` (not a whole number, or not a faction id of the map); a map faction with no territory gives `ok([])` (the internal function is not called, since it throws); otherwise the internal result's `factions` only.
- `livingFactions(map, state)`: map validation errors, `invalid-state`; otherwise the internal `livingFactions(state)`.
- Equivalence (FR-312): for every map of the existing golden fixtures and the dev map, seeds 0 to 999, chaining `playRoundWithSeed` with a constant seed from `getState(map, 0, 0)` gives exactly `getState` and `getRounds` at every round 0..T.
- Cost: validating the map on every call is the 001 style; the server calls these a few times per step, so no cache is added (a cache would be a later, measured change).

### 17.2 Store decisions (planner, M2b)
- PD9. One SQLite file per server; `PRAGMA journal_mode = WAL`, `synchronous = FULL`, `foreign_keys = ON`, `locking_mode = EXCLUSIVE` and an immediate write transaction at open to take the lock; a second process (or connection) gets `database-locked` and the server refuses to start (FR-291, FR-292 durability). `PRAGMA user_version` = 1; 0 means a new file (schema created in one transaction); any other value refuses to start. Discarded: `journal_mode = DELETE` (slower commits, same durability).
- PD10. Every decision runs synchronously inside one `BEGIN IMMEDIATE ... COMMIT` (node:sqlite is synchronous and the process single-threaded, so per-match serialisation, FR-295, holds by construction); events are published to in-process subscribers only after `COMMIT` returns (FR-290). Discarded: an async queue per match (no concurrency to manage).
- PD11. The absorber and the pending state are never written: they exist only inside `performStep` (PD7); `records` and `states` get a row only for applied rounds. Round seeds are never stored (recomputed from the plain secret, D14).
- PD12. Credential digests: `sha256("mbrg/credential/v1/" + text)` hex for host tokens (stored) and for memo scopes (operator credential, host token, client credential); no credential text is ever written; the creation-reply memo holds the plain host token for 24 h (D23) and is purged at the first tick after retention.
- PD13. A storage failure inside a decision rolls back, the reply is `unavailable`, and a failed clock step is retried by the scheduler 3 s later; when it is retried after its instant + 1 s it is overdue and follows FR-248 (late, anchors shifted).

### 18.2 The request pipeline, in the FR-301 order
Every request runs these stages in order; the first stage that fails answers, so the reply kind is the first applicable in the fixed order.
1. **Identify and admit** (`rate-limited`): the method gives the class (GET and OPTIONS are reads, POST a command); the `Authorization` header is read as `Bearer <token>` (anything else is anonymous); the token is compared, in time independent of its content, with the operator credential and every client credential (all comparisons always run) and, only for `POST /matches/{id}/advance`, with the match's host token (`hostTokenMatches`); a token that matches nothing is anonymous. The limiter admits the request under its credential key or, when anonymous, its address key (the TCP peer; forwarding headers are not trusted). A request over a limit is answered 429 here, before any routing.
2. **Route** (`unknown-path`, `method-not-allowed`): the table of 18.3. `OPTIONS` on a known path is the preflight (CORS, 204); on an unknown path `unknown-path`.
3. **Body** (`too-large`, then `invalid-request`): a `Content-Length` above 4,096 is answered at once without reading the body; a body without length (chunked) is counted while read and answered as soon as it passes 4,096; a body that is not UTF-8 JSON of the required type, or a query that breaks the rules of the route (unknown parameter, `limit`, `cursor`, `playerId`), is `invalid-request` naming the first failing field.
4. **Shape** (`invalid-request`, `invalid-player-id`): the readers of the protocol (`readCreation` shape part, `readAdvance`, `readSubmission`) run before the credential check, as FR-301 orders them.
5. **Authorization** (`forbidden`): routes that need a client credential (submission, own predictions) require one; creation and advance are authorized by the service (operator credential, host token) in its own order.
6. **Per-player limit** (`rate-limited`): a submission is counted under (match, player id) once its body is read; if it is over, the ticket of stage 1 is cancelled, so a rate-limited request is counted nowhere (FR-299 (c)).
7. **Decision**: the service call; its outcome (success, or an `ErrorReply`) is mapped by `status.ts` and encoded by the protocol encoders.
8. **Unexpected exception**: caught at the top; logged once through the closed `LogEvent` (18.7); answered 500 with the body `{"kind":"unavailable"}` (C1); a response already started is ended, nothing is written twice.

### 18.6 Limiter (pure)
Per key an array of accepted request instants; `admit(keys, now)` prunes entries older than 60,000 ms, refuses when any key already holds its limit, and otherwise records `now` under every key and returns a ticket; the wait of a refusal is the largest over the exceeded keys of `ceil((oldest + 60,000 - now) / 1000)` with a minimum of 1. `ticket.cancel()` removes the instants it recorded. Keys exist only for the operator, the configured client namespaces, host tokens of existing matches (checked against the store before a key is created), addresses and (match, player id) pairs; a key with no instants is deleted at the next prune, and a full sweep runs every 1,000 admissions, so memory follows the traffic of the last minute. State is in memory only (FR-299 (d)).
### 18.7 Logging policy (C5)
- Output is a closed union `LogEvent` (`listening`, `start-report`, `step-failed`, `request-failed`, `shutdown`, `fatal`, `listen-failed`) rendered by `main.ts` as one JSON line: lifecycle events on stdout, failures on stderr. The union has no field that can hold a credential, token, secret, round seed, player id, choice, path, query or body.
- A cause is described by `describeError`: error name, `code` when it is an upper-case identifier, the SQLite result code and `errstr` when the platform gives them, the cause chain to depth 3, and up to 8 stack frames as `function file:line`. **The message is never logged** (it may quote values; Node's JSON errors quote the input).
- There is no per-request access log (paths carry match ids and query strings carry player ids). Client errors (4xx) and expected 503 from a storage failure are not logged per request; the failure of a clock step and any 500 are.
### 18.8 Entry point and shutdown
`main.ts`: `readSettings` (problems named, exit 1) -> `openStore` -> `createMatchService({ ..., onFailure })` -> `service.start()` (log the counts of the report) -> `createServer(...).listen(port, host)` -> `listening` event with the bound port -> signal handlers. `SIGINT`/`SIGTERM`: stop accepting, close idle connections, wait up to 5,000 ms for requests in flight (the grace period is armed through the scheduler interface, so timers stay in `scheduler.ts`), close the remaining connections, `service.close()` (cancels every wake-up, closes the store and releases the lock), exit 0; a second signal exits at once with 1. `uncaughtException`/`unhandledRejection`: log `fatal` through the closed union, run the same shutdown, exit 1. A listen error (port in use) logs `listen-failed` with the error code, closes the service and exits 1. Windows cannot deliver a signal to a child process, so the real-signal test runs on POSIX (CI Linux) and is skipped on Windows; the shutdown function itself and the signal wiring (a fake process emitter) are tested on both.

### 19.2 Wire format (E2)
- Path `GET /matches/{id}/events`, credential-free (FR-285); the only query parameter is `lastEventId` (FR-289 (d) "address parameter"); `OPTIONS` is the preflight; other methods 405 with `Allow: GET, OPTIONS`.
- Starting number: the `Last-Event-ID` header wins over `lastEventId` (an `EventSource` reconnects to the same address, query included, and adds the header with the newest id). A value is `0` or digits without a leading zero; past 2^53 - 1 it is `beyond` (no event will ever be later); anything else (sign, leading zero, empty, two header values, a fraction) is 400 `invalid-request` naming `Last-Event-ID` or `lastEventId`. Without either: live only (FR-289 (e)).
- Before the first byte every failure is an ordinary JSON reply in the FR-301 order: 429 (per-minute read limit or open-stream limit), 404 `unknown-path`, 405, 413 (FR-298), 400, 404 `unknown-match`, 503 `unavailable` (storage failure, or the server is shutting down).
- 200 headers: `Content-Type: text/event-stream`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, the CORS headers of a read (18.4b: `*` without `Authorization`, the allowed origin with it), no `Content-Length` (chunked); flushed at once.
- One frame per event: `id: <seq>` and `data: <encodeEvent(event)>`, then a blank line. No `event:` line (the payload carries `type`, so one `message` handler sees every type, future ones included), no `retry:` line (the client's reconnection policy is M5, FR-307).
- Heartbeat: the comment frame `:\n\n` to every open stream every 14,000 ms (one hub wake-up through the Scheduler interface, armed only while a stream is open). It carries no data and no id, so `Last-Event-ID` does not move (FR-289 (f)). 14,000 keeps the 15 s bound with the 1,000 ms margin of NFR-50 for a late timer.

### 19.3 Replay and live without gaps or duplicates (FR-289 (b), (d), (e), FR-290, FR-294)
- The service publishes a decision's events synchronously right after its commit (PD10). `hub.open` runs in ONE synchronous turn: `service.eventsAfter(matchId, n)` (stored events with seq > n and the stored `lastSeq`), then `writeHead`, then the replay as one write, then the registration. No commit can fall between the read and the registration (no `await`), so nothing is missed and nothing is sent twice.
- Each stream keeps `last` (n, or the last replayed seq; without a number the stored `lastSeq`) and writes only live events with seq > `last` (a defensive filter, tested by feeding the subscriber an old event).
- Events stored by an earlier process and never sent (a kill after `COMMIT`, a kill during `start()`) are in the store and come back in the replay with their original numbers (FR-294).
- A number above the latest gives no events and no error now, and the filter keeps applying: later events with seq <= n are not sent (the literal "every later event"; E5).
- Only stored events are framed, and stored events are built from the public view (PD7, FR-290): the stream has no other data source, so it cannot carry anything unrevealed (FR-254, FR-257). A stream never receives another match's events.

### 19.4 Stream limits (FR-299; E3, E7)
- Open-stream gauge, pure, in memory: key `streams:<digest>` with limit `limits.streams` (default 50) for the operator and each client credential (C4: the operator uses the client values); otherwise `streams-address:<address>` with `limits.anonymousStreams` (default 5). A host token on the stream route is anonymous (only the advance route resolves host tokens, PD16).
- Checked at stage 1, only for a found stream route, together with the per-minute admission: opening a stream is one read of the per-minute read limit. A refusal of either is 429 and the read ticket is cancelled (counted nowhere, FR-299 (c)); `Retry-After` is the largest wait over the refused limits: the per-minute wait when that limit refused, and STREAM_RETRY_SECONDS = 15 when the gauge refused (proposed D28: the instant an open stream closes cannot be known).
- The lease taken at stage 1 is released exactly once: at the reply when the request ends without a stream (any 4xx or 5xx, a client gone during the body), or when the stream closes (client gone, slow-client drop, shutdown).
- No server-wide stream cap: the spec has none (risk 19.12).

### 19.5 Back-pressure and slow clients (E7)
- Before each live write and each heartbeat, a stream whose `res.writableLength` exceeds STREAM_BUFFER_LIMIT (1 MiB) is destroyed; its client reconnects with `Last-Event-ID` and the replay gives what it missed (events are durable), so dropping it loses nothing. The replay is one write and is not checked against the limit (it is bounded by one match's stored events).
- A write to an ended or errored response is skipped; a write that throws closes only that stream. Nothing is logged (no per-request log, 18.7).

### 19.6 Shutdown and restart (plan 18.8)
- `shutdown.begin`: after `shutdown-start`, `streams.closeAll()` unsubscribes the hub, cancels the heartbeat, ends every stream (`res.end()`) and makes later opens answer 503 `unavailable`. The ended responses leave idle connections, closed by the existing `res` 'close' hook, so a shutdown with only streams open ends before the grace (`forced: false`) instead of waiting 5 s.
- After a restart a client reconnects with `Last-Event-ID` and gets the replay (19.3).

### 19.7 Finished and halted matches (E4)
A stream on a finished or halted match opens like any other, replays, then gets heartbeats only and stays open until the client closes it (the M5 viewer closes it on `match-finished` or `match-halted`). Discarded: closing it after the replay (an `EventSource` reconnects about 3 s later, forever) and answering 204 to stop the reconnection (not in FR-289).

### 19.8 What an event stream carries (FR-287 order)
The order inside one decision is the core's (`performStep`, PD7) and the hub writes the events of a decision in the order it receives them: phase-1 close `phase-closed`, `victim-revealed`, `schedule`; phase-2 close `phase-closed`, `schedule`; with L2 = 0 `phase-closed`, `round-applied`, `schedule`; application k < T `round-applied`, `schedule`; round T `round-applied`, `match-finished` (no `schedule`); a halt `match-halted` only. The `results` event of FR-287 (d) is not produced before M4 (scoring): M4 inserts it after `victim-revealed` and after `round-applied` and updates the sequences pinned by M3b' T2' (E6). ### 20.2 Where scoring happens (secrecy and determinism)
- The core stays pure and never reads predictions: `performStep` returns, next to the rows and events, `scored: ScoredPhase[]`, built only from what the step makes public: at a phase-1 close `{ kind: 'victim', round: k, answer: victim, worth: living.length }` (n, FR-271); at an application `{ kind: 'absorber', round: k, answer: record.absorber, worth: victim.candidates.length }` (d, FR-272) and, when the match finishes, `{ kind: 'winner', answer: winner }` (FR-273, each prediction worth its stored `winnerCandidates`). A halt returns no `scored` and no `results` event (FR-251 (c)). The absorber enters `scored` only in the application, where `applied` already carries it (PD7 unchanged).
- The shell, inside the decision's one transaction, for each scored phase: `rows = scorePhase(phase, store.predictionsOfPhase(matchId, kind, round))`, then `store.putResults(matchId, rows)`. Write order of a step (extends 17 / matches.ts header): `updateMatch`, `putRecord`, `putResults`, `putStep`, `appendEvents`; publication after the commit (FR-290). So the results are stored before their `results` event is published, a kill before the commit loses both, and the redo (late step after a restart) scores the same stored predictions again: same rows (FR-294, NFR-57).
- Every stored prediction of the phase counts (PD29): FR-266 refuses a submission at or after its cutoff and FR-295 serialises it against the closing step, so every stored row was stored before the cutoff and before the step began; the scorer does not re-check instants.
- Pseudocode:
```
scorePhase(phase, predictions):            // predictions ordered by player id
  for (playerId, p) in predictions:
    correct = p.choice == phase.answer
    worth   = phase.kind == 'winner' ? p.winnerCandidates : phase.worth
    row(playerId, phase.kind, phase.kind == 'winner' ? 0 : phase.round, p.choice, correct, correct ? worth : 0)
rankLeaderboard(totals):                   // totals: playerId, total, correct per kind
  sort by total desc, then playerId by code unit
  rank(i) = i == 0 or total(i) < total(i-1) ? i + 1 : rank(i-1)      // competition ranking 1, 1, 3
scoredPhaseCount(view) = 2 * N + (view.victim?.round == N + 1 ? 1 : 0)   // the generation (2T when finished)
isScored(view, k, 1) = k >= 1 and (k <= N or view.victim?.round == k);  isScored(view, k, 2) = k >= 1 and k <= N
```
`isScored`, `scoredPhaseCount` and `readResultsRound` take only `appliedRounds`, `victim` and `stage` of the public view (NFR-47 (b) spirit: nothing unrevealed decides a read).

### 20.3 Scoring rules (pure; FR-271 to FR-274, D12, P27)
- Victim: correct iff it names the victim; worth n = the factions living at N (`PublicVictim.living.length`, victim included).
- Absorber: correct iff it names the absorber; worth d = the absorption candidates of the victim in the state at k − 1 (`PublicVictim.candidates.length`); d = 1 gives 1.
- Winner: correct iff it names the winner; worth the winner candidates stored at its last change (FR-267); a prediction for a faction eliminated later scores 0.
- One row per prediction, correct or not (0 points): the leaderboard needs all-zero players (D23) and the phase results list every player that predicted (FR-275). No streak bonus, never negative (FR-274).
- Leaderboard row: `rank`, `playerId`, `total`, `correctVictims`, `correctAbsorbers`, `correctWinner` (0 or 1); ranked by total, equal totals share a rank (1, 1, 3), then by player id (code-unit order, the SQLite BINARY order of these ASCII ids).

### 20.5 Storage, persistence and restarts (G7)
- **No schema change**: v1 already has `results` with the needed columns and the primary key (`match_id`, `round`, `kind`, `player_id`), which serves the phase results (keyset on player id) directly; the player results and the leaderboard scan the match's rows (no index: an index would be a schema change, out of scope; risk 20.13). `SCHEMA_VERSION` stays 1; `results.correct` is 0 or 1; the winner row has round 0.
- **Refusals of `putResults`** (`invalid-write`, read in the same transaction after `updateMatch`; defence in depth for FR-256 and FR-270, since a premature `correct` bit would reveal an outcome): an absorber row of a round above N; a victim row of a round above N + 1, or of N + 1 while the match row holds no victim; a winner row unless the stage is `finished`; a duplicate key (a phase is scored once).
- **Databases written before M4**: phases closed by the earlier code have no rows, and nothing scores them later (no migration: spec "Out of scope: schema migrations"; FR-291 leaves migrations to later plans). Accepted because no database outside tests exists (every file database is a temporary test or load-script file). Discarded: `user_version` 2 refusing v1 files (deletes nothing useful, but changes a pinned startup rule); a scoring migration at open (a second scoring path).
- **Restart and replay**: a restart after a scored step reads the rows from the store; the generation comes from the stored match, so a leaderboard cursor issued before a restart stays valid when nothing new was scored; events stored but not sent (a kill after `COMMIT`) are replayed with their numbers, the `results` event included (19.3).
- **Storage anti-spoiler check** (`helpers/db-scan.ts` `storedFutureViolations`, NFR-47 (d)): the refusals above as scan rules, plus a `results` event of a round above N + 1, a `results` (N + 1, 1) event before the reveal and a `results` (k, 2) event with k above N.

### 21.3 Client architecture (pure core, effectful shell)
```
 page address --chooseScene--> debug (dev only, ui/main.ts, unchanged) | message | live
 live: inputs (public data read, state read, record read, map files verified, event frame, stream opened/dropped,
        read failed, digest result, timer due, navigation)  --reduce(model, input)-->  { model, effects }
       effects (read public, read state j, read record j, read map files, open stream { after, header }, close stream,
        hash state text, arm timer, draw round, play step, show panel) --live-runner--> net / timers / web-crypto / map-view
```
- `reduce` is a pure function of (model, input) where every input carries the monotonic instant `at` read by the shell from `ui/clock.ts` (NFR-25): no DOM, no WebGL, no clock, no network; it is tested in Node with literal inputs. The shell runs effects and feeds their results back as inputs; it holds no match data of its own.
- The model (`LiveModel`): `matchId`, `mapDigest`, `totalRounds`, `timing`, `stage`, `appliedRounds` N, `held` (owners of the received rounds j <= N and records 1..N received), `displayed` (the round on display) and `following` (displayed === N when the last change happened), `lastSeq`, `reported` `{ value, at }` (largest reported time received and the instant it arrived), `schedule`, `victim` (the FR-288 fields), `winner`, `haltReason`, `connection` (`connecting`, `open`, `waiting { attempt, until }`, `closed`), `fatal` (an error that ends the scene).
- Reported-time estimate: `estimateAt(model, at) = reported.value + (at - reported.at)`, never decreasing (it is spec 009's definition, so 009 reuses it). Countdown = max(0, anchor - estimate), anchor C1 in `phase-1`, C2 in `phase-2`, A in `locked`; none with timing `manual` or when not running (FR-305).
- Spec 009 seam: on a fresh `victim-revealed` the model shows the victim at once (D19, no animation in 008); on `round-applied` it emits the `play-step` effect with the received `StepData`. Spec 009 later inserts its tours between the event and those effects; M5 adds no tour hook, dim input or `reveal` parameter (not in this spec).

### 21.4 Load and verification sequence (FR-303, FR-306, FR-308)
```
chooseScene(search, dev):
  match and seed both present            -> message 'both'          (every build)
  match present: malformed or repeated   -> message 'bad-match'     (no request is sent)
  match present                          -> live { matchId, round?, camera? }
  seed only / neither                    -> dev ? debug : message 'need-match'
live start:
  if !digestAvailable()                  -> fatal 'insecure-origin' (FR-308: fail closed, before any request)
  readPublic(matchId)                    -> 404 unknown-match: fatal 'unknown-match' (no retry); network or 5xx: retry (21.7)
  readMapFile(mapId, f) for the 3 files  -> raw bytes; sha256Hex(mapDigestBytes(files)) !== mapDigest: fatal 'digest-mismatch'
  decode (TextDecoder utf-8, like response.text()), parsePackage, checkPackage, capabilities, colours (the debug path's checks)
  held[N] = public.state; draw N (or the address round j <= N, read with its record, D31)
  openStream(after = public.lastSeq, as the `lastEventId` parameter)           (FR-289 (b), FR-307 first connection)
```
No state, record or event is drawn before the map digest matched; a fatal error shows one Spanish message and no scene.

### 21.5 Events (one `message` path, E2; FR-287, FR-289)
| Frame | Handling |
|---|---|
| `seq <= lastSeq` | ignored (a replay overlap or a duplicate): no change, no effect |
| `seq > lastSeq + 1` | gap (cannot happen with the server of 19.3; defensive): close the stream, read the public data again, rebuild the model, subscribe with its `lastSeq` |
| unknown `type` with a whole `seq` | consumed: `lastSeq = seq`, nothing else (forward compatible, E2) |
| known `type`, payload refused by `readEvent` | protocol fault: close, wait by the retry schedule, resync as for a gap |
| `phase-closed` | `lastSeq`; the stage follows the next `schedule` (or `round-applied` with L2 = 0) |
| `victim-revealed` | victim fields; panel shows the victim's name at once (FR-305, D19); reported time |
| `round-applied` (k) | k must be N + 1 (else resync); `applyRecord(held[N], record)`, effect `hash-state`; on the matching digest: `held[k]`, record k, N = k; if `following`, effect `play-step` (k - 1 -> k) and displayed = k at once (FR-303); else controls only (D32); on a mismatch: effect `read-state k` and an instant change to it (FR-304) |
| `results` | consumed; the viewer shows no results (FR-305); the web test client reloads its results (M5') |
| `schedule` | stage, anchors, reported time |
| `match-finished` | winner, stage `finished`, close the stream (E4) |
| `match-halted` | reason, stage `halted`, the victim fields stay (FR-251 (e)), close the stream |
Every reported time received raises `reported` only if larger (never decreases).

### 21.6 Rounds held, requests and navigation (FR-303, FR-304)
- `canRequest(model, j)` is true only for 0 <= j <= N (states) and 1 <= j <= N (records); every read effect is built through it, and a test over a whole match asserts that no request path ever names a round above the N of that moment (the client half of "future rounds never reach the client").
- Stepping backwards over applied rounds stays allowed (FR-304): the controls cover 0..N (`navigate(displayed, N, action)`); a round not held is read (`/states/j`, `/records/j + 1` for the step data) and kept (public data). Nothing about round N + 1 is held except the FR-288 fields while revealed.
- The state at N + 1 is built only from the received record (transfer of the listed territories to the absorber; a listed territory not owned by the eliminated faction in `held[N]` is a mismatch) and checked against the event's state digest (SHA-256 of `stateText`, the browser's crypto). No engine round step, no draw, no sim import in any live module (scan, FR-304).

### 21.7 Connection policy (FR-307, FR-289 (d), (e))
- Retry schedule after a failure (network error, 5xx, 429, an unreadable reply): 1, 2, 4, 8, 16 s, then every 30 s; a 429 waits max(schedule, `Retry-After`); a success resets it. While waiting, the last drawn state stays and the panel shows the Spanish notice with the time of the next attempt.
- Stream drop (the body ends or errors, or no byte for 45,000 ms: three heartbeats of 14 s plus margin, H10): the first reconnection is immediate, later failures follow the schedule; the reconnection sends the `Last-Event-ID` header with the last sequence number received (FR-289 (d) letter: the address parameter is for the first connection only); the replay is applied through 21.5, so nothing is missed or applied twice.
- `unknown-match` on any read: fatal, no retry. A non-200 stream reply follows the same classification. The viewer never opens a stream without a number (FR-289 (e) would lose events).
- Finished or halted: the stream is closed by the viewer and not reopened.

### 21.8 Panel (FR-305, NFR-56)
Spanish texts, all in `core/strings.ts`: the title of the live scene, "Ronda N de T", the stage (five texts), the countdown in `H:MM:SS` / `M:SS` to the next scheduled step in every running stage (none with `manual`), the victim line during `phase-2`, `locked` and `halted` after a reveal, the winner when finished, the halted notice with one text per reason (`map-changed`, `isolated-faction`, `victim-mismatch` are data, mapped to Spanish), the connection notice, the legend (faction names and alive / eliminated, as the debug legend), the controls (first, previous, next, last, reset). No seed, no pointer readout, no timings, no results (not in FR-305). Error kinds stay English identifiers inside Spanish templates (NFR-28).

### 21.9 Address (FR-306, P20, D31)

### 21.12 CORS and wire details on the client
Viewer and credential-free client reads: `fetch(url, { credentials: 'omit' })` with no custom header, so a cross-origin GET is a simple request (no preflight) answered `*` (18.4b); the stream reconnection adds only `Last-Event-ID` (preflight allowed by E8). Credentialed requests (submission, own predictions) send `Authorization: Bearer` and `Content-Type: application/json` from an allowed origin. Bodies are read as text and parsed with `JSON.parse`, then by the protocol readers (untrusted input).
