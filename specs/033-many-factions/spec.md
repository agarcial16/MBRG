# Spec 033 — Many Factions in the Viewer
Status: draft
Tier: Light SDD (viewer `apps/web` now; importer report `tools/build-map` when PR #94 merges; **no map format, protocol, `packages/shared`, `packages/sim`, `apps/server`, or `apps/bot` change**). Depends on 004 (viewer rendering, capabilities, colour assignment), 005/009/013 (fronts, reveal tours, chosen-faction outline), 029 (viewer count refusal), parallel bug fix `fix/world-palette-exhausted` (sea-only adjacency as a soft preference), and 028 (importer `viewerLimits` report, PR #94). Ids: FR-640 to FR-646, NFR-160 to NFR-164 (outside the `packages/sim` traceability ledger, clear of all archived specs and Spec 032 PR #96).

## Context and goal
The imported historical map "world in 1815" (`world-1815-4`: 302 factions, 410 land territories, 14 sea zones, 424 total entries, 2048 × 2048) is refused by today's viewer: *"El mapa tiene 302 facciones y el visor puede dibujar como máximo 255."* In addition, even with the 255 count limit lifted, large world maps (`world-1815-4` at **Goa** and `maps/world-countries` at **Dinamarca**) hit `palette-exhausted` under the 12-colour palette and strict sea-clique rule.

User decision (quoted): **"Subir el límite del visor"** — raise the viewer's capacity rather than merging factions in curation. This spec implements follow-up **V2 (many factions)** anticipated by specs 028 and 029, **building directly on `fix/world-palette-exhausted`** (which relaxes sea-only adjacency to a soft preference when the palette runs out while keeping land-adjacent neighbours strict).

### Real limits verified in the codebase today
1. **Map format & `ids.png` territory encoding (no limit bottleneck):** `ids.png` is an 8-bit RGB PNG (24 bits per pixel: `R × 65,536 + G × 256 + B`), supporting territory and faction ids `1..16,777,215` (`0xffffff`, `0` = outside). `packages/shared`, `packages/sim`, `packages/protocol`, `apps/server`, and `apps/bot` impose no 255-faction or 65,535-territory cap.
2. **Viewer territory-entry table:** dense 16-bit entry index (two bytes per pixel, `0` = outside, `1..65,535` = land + sea entries). Lookup tables are 1D strips (`entries + 1` texels wide), bounded by WebGL 2's `maxTextureSize` (guaranteed ≥ 2,048).
3. **Viewer faction encoding (current bottleneck #1):** per-entry owner table uses a single 8-bit channel (`0` = none, `1..255` = faction index), capping the viewer at **255 factions**. Pick-outline and reveal-tour inputs also guard against indices > 255 (even though shader uniforms are already 32-bit integers). The faction-colour table is `factions + 1` texels wide; because every faction owns at least one land territory, `factions + 1 ≤ entries + 1` always holds on valid maps.
4. **Viewer palette & neighbour rule (current bottleneck #2):** fixed 12-colour palette; step 2 originally forbade reusing a colour held by any direct candidate (land neighbours **plus** every faction touching a shared sea zone). Large ocean sea zones create huge cliques (`world-1815-4` sea zone 417 touches **77** factions; `maps/world-countries` sea zone 197 touches **54** factions), while colonial empires create non-planar land borders (max land degree 69 in 1815, chromatic number 5; greedy in faction order needs 6). Relaxing sea-only adjacency (`fix/world-palette-exhausted`) prevents ocean cliques from exhausting the palette, enlarging the curated base palette from 12 to ~20 colours gives rich visual variety across 200–300+ faction maps, and a deterministic procedural last resort guarantees even pathological non-planar land graphs up to 65,535 factions never fail.
5. **Importer report (`viewerLimits`, Spec 028 / PR #94):** warns on `textureAbove2048`, `entriesAbove65535`, `factionsAbove255`, and `paletteExhaustedFaction` (using an importer-local copy of the viewer's rule).

### Why the new faction ceiling is 65,535
Every faction in a valid map owns at least one land territory, so `factions ≤ land territories ≤ entries ≤ 65,535`. Widening the owner table from 1 byte per entry (max 255) to **2 bytes per entry (max 65,535)** — matching the 16-bit encoding already used for the entry index — aligns the faction ceiling with the territory ceiling at minimal cost (850 B for 1815's 424 entries; 128 KB at the 65,535 extreme). Lower arbitrary caps such as 1,023 save zero texture bytes over 16-bit two-channel storage and would still reject Spec 028's 8,132-faction municipal stress proof and 9,999-faction importer cap.

### Goal
Enable the viewer to load, colour, draw, step, pick, and reveal any valid map up to **65,535 factions** (within device texture limits), enlarge the hand-picked cartographic base palette (12 → ~20 colours matching the Spec 031 viewer style) with procedural colours only as a last resort, build on `fix/world-palette-exhausted`'s soft sea-adjacency relaxation, keep clear Spanish refusals for remaining limits, and align the importer's `viewerLimits` report when PR #94 merges.

## Users
- **Viewer user (spectator / player):** opens a match on a large world or historical map (hundreds to thousands of factions) and sees every faction rendered with clear borders, rich cartographic colours, and distinguishable neighbours instead of a count or palette refusal.
- **Map author / operator:** imports a 300+ faction map and gets accurate `viewerLimits` warnings reflecting what the viewer actually supports.

## User stories
- US-1. As a viewer user, I want maps with more than 255 factions (such as the 302-faction 1815 world map) to load and render cleanly without hitting a 255-faction or palette refusal.
- US-2. As a viewer user, I want factions that touch across land borders (and, as a soft preference, across shared sea zones) to have distinguishable, hand-picked cartographic colours that stay fixed throughout the match.
- US-3. As a map author, I want the importer's `viewerLimits` report to reflect the raised faction ceiling and updated colour rules once PR #94 merges.

## Definitions
- **Land-adjacent neighbours:** two distinct factions that own 4-adjacent land territories with mutual neighbour links in the map.
- **Sea-adjacent candidates:** two distinct factions that are not land-adjacent but both own land territories mutually linked to the same sea zone (direct candidates at round 0 via sea, 002 FR-75/FR-76).
- **Direct candidates:** the union of land-adjacent neighbours and sea-adjacent candidates at round 0.
- **Original 12 base colours:** the existing 12 curated viewer colours in their fixed assignment order (004 FR-142).
- **Enlarged curated base palette:** the original 12 base colours in their exact order (`0..11`) followed by ~8 newly hand-picked cartographic colours (`12..~19`, total ~20), mutually distinguishable and styled to match Spec 031.
- **Procedural palette:** a deterministic, seedless last-resort sequence of at least 65,535 pairwise distinct RGB colours extending the curated base palette.
- **Colour separation:** a deterministic distance metric in perceptual or weighted RGB space (exact formula and threshold pinned in implementation tests) ensuring two procedural colours are visibly distinguishable rather than differing by a few RGB units.

## Functional requirements
- FR-640: THE SYSTEM SHALL support loading, drawing, round stepping, colour-front animation, reveal-tour dimming, and chosen-faction outlining for valid maps with up to **65,535** distinct factions (indices `1..65,535`, with `0` reserved for no owner), without changing the map package format or any non-viewer package.
- FR-641: THE SYSTEM SHALL enlarge the curated base palette from 12 to ~20 hand-picked, cartographic, mutually distinguishable RGB colours matching the Spec 031 viewer aesthetic, keeping the original 12 base colours first in their exact order (`0..11`). All ~20 curated colours SHALL participate together in steps 1 and 2 (factions 13..~20 without preferred colours receive unique curated colours before any reuse begins; `maps/dev` stays byte-identical, larger existing maps may shift colours slightly, and existing 12-colour step-2 unit tests are updated accordingly). Every curated colour SHALL be pairwise distinct, distinct from the sea colour, background colour, and every border class colour, never near-black (RGB channel sum > 120, preserving 004 FR-143), and never near-white (keeping white labels and the white selection outline legible). Preferred colours from presentation data SHALL still be used verbatim as given.
- FR-642: WHEN even the enlarged curated base palette (~20 colours) is exhausted by a faction's land-adjacent neighbours, THE SYSTEM SHALL fall back as a last resort to a deterministic, seedless procedural palette of at least **65,535** pairwise distinct RGB colours computed solely from the map and presentation data (independent of seed, round, time, or camera); every generated colour SHALL be pairwise distinct from every other procedural colour and from all curated base colours, distinct from the sea colour, background colour, and every border class colour, never near-black (RGB channel sum > 120), and never near-white.
- FR-643: WHILE assigning colours to factions without a preferred colour (in faction order, building on `fix/world-palette-exhausted`), THE SYSTEM SHALL enforce neighbour distinguishability in priority order:
  1. **Unique curated colour:** first curated base colour unused by any already-coloured faction and unequal to any preferred colour of the map;
  2. **Curated avoiding all direct candidates (land + sea):** first curated base colour unused by any already-coloured or preferred direct candidate at round 0;
  3. **Curated relaxing sea-only adjacency (soft sea preference, strict land neighbours — `fix/world-palette-exhausted`):** first curated base colour unused by any already-coloured or preferred **land-adjacent** neighbour (preferring the colour with the fewest sea-adjacent collisions, ties broken by palette order);
  4. **Procedural last resort (FR-642):** ONLY when all curated base colours are blocked by already-coloured or preferred **land-adjacent** neighbours, pick the first procedural colour unused by any direct candidate with at least the minimum colour separation from all already-coloured and preferred land-adjacent neighbours, relaxing sea-adjacent distinctness first and then separation distance if a pathological land graph exhausts the primary band.
  Two land-adjacent factions SHALL NEVER receive the same colour (unless forced by identical preferred colours, which package validation forbids), and every valid map up to 65,535 factions (including `maps/world-countries` and `world-1815-4`) SHALL be coloured without failure.
- FR-644: THE SYSTEM SHALL keep refusing unloadable packages before drawing, with Spanish messages from the UI strings module in strict order: (1) package, map, presentation, and id-image validation errors (004 FR-133); (2) viewer count limits read dynamically from the drawing table sizes — territories above 65,535 named before factions above 65,535 (029 FR-586 to FR-589); (3) browser graphics capability limits — missing WebGL 2, or `maxTextureSize < max(width, height, entries + 1, factions + 1)` (004 FR-135); and (4) defensive `palette-exhausted` refusal (keeping `STRINGS.paletteExhausted`) only if a caller explicitly supplies a finite custom palette without procedural extension (OQ2).
- FR-645: WHEN the displayed round changes, THE SYSTEM SHALL update only per-entry owner data (at most 2 bytes per entry plus the outside slot, never pixel data), keeping borders, colour fronts, reveal dimming, and chosen-faction outlines exact for every faction index in `1..65,535` (including indices ≥ 256, where both bytes are non-zero).
- FR-646: WHEN `feat/028-map-importer` (PR #94) merges, THE SYSTEM SHALL update the importer's `viewerLimits` report section to raise the faction-count warning threshold from 255 to 65,535 (no faction-count warning for 256..65,535 factions), SHALL align its palette-exhaustion check with FR-641 to FR-643 so maps coloured without exhaustion emit no `paletteExhaustedFaction` warning, and SHALL keep reporting `requiredTextureSize`, `textureAbove2048`, and `entriesAbove65535` unchanged (OQ3).

## Non-functional requirements
- NFR-160 (Performance bounds):
  - Pure colour assignment (including neighbour-graph construction) SHALL complete in at most **50 ms** for a 500-faction map (including `world-1815-4`: 302 factions, 424 entries) and at most **250 ms** for a 10,000-faction synthetic map in Node (no O(F²) scan over total factions).
  - In the browser on the reference machine (Windows 11, Chrome/Edge, 1920 × 1080): `maps/dev` keeps all 004 NFR-24 / 009 NFR-43 budgets; on `world-1815-4` (2048 × 2048, 424 entries, 302 factions), median frame time ≤ **16.7 ms**, 95th percentile ≤ **33.3 ms**, round change ≤ **200 ms**, and time to first frame measured and recorded in the PR (target ≤ **3,000 ms**, split between table/colour setup and initial label layout).
- NFR-161 (Purity and determinism): colour assignment, procedural palette generation, owner-table encoding, and count/capability checks are pure, deterministic functions with no DOM, WebGL, clock, I/O, or system randomness, verified by Node tests and the existing purity scan.
- NFR-162 (Scope and compatibility): changes live only in `apps/web` now and `tools/build-map` when PR #94 merges (OQ3). Zero changes to `packages/shared`, `packages/sim`, `packages/protocol`, `apps/server`, `apps/bot`, the map format, `MatchState`, `maps/dev`, or existing goldens. No new third-party dependencies.
- NFR-163 (Language): code, comments, error kinds, and report labels stay in English; all viewer user-visible messages stay in Spanish in the single UI strings module, with every string key used by code.
- NFR-164 (Visual verification): before merge, desktop and mobile screenshots of the viewer rendering `world-1815-4` (round 0 overview, zoomed land-border clusters around Goa/India and Central Europe, and a post-absorption round step), `maps/world-countries` (previously failing at Dinamarca), and a `maps/dev` regression view are saved under `.claude/review/033-many-factions/` (gitignored), posted as Markdown images, and accompanied by a desktop and mobile before/after comparison widget.

## Edge cases
- **Faction index 255, 256, and 65,535:** exact encoding/decoding across the 8-bit/16-bit boundary (`255`, `256`, `257`, `65,535`) in owner tables, border classification, colour fronts, reveal-tour lighting (`lit`), and chosen-faction pick outline (`pick`).
- **Count boundary (`65,535` vs `65,536`):** a synthetic map with 65,535 territories and 65,535 factions passes `checkCounts`; 65,536 territories is refused with `too-many-territories` (and because valid maps satisfy `factions ≤ entries`, any valid map exceeding 65,535 factions also exceeds 65,535 entries and names territories first per 029 FR-588, while `checkCounts` still checks factions dynamically against the table size per FR-589).
- **Large sea-zone clique (`world-1815-4` sea zone 417 with 77 factions; `maps/world-countries` sea zone 197 with 54 factions):** sea-only adjacency relaxes cleanly in step 3 while keeping all land-adjacent neighbours distinct within the ~20 curated base colours (zero procedural colours needed); Goa and Dinamarca load cleanly.
- **High-degree land hub (`world-1815-4` with land degree 69, or a synthetic 25-clique / 300-spoke land graph):** when a hub's land-adjacent neighbours block all ~20 curated colours, step 4 draws from the procedural last resort with colour separation; no crash or exhaustion.
- **Custom finite theme palette without procedural extension:** when all colours are blocked by land-adjacent neighbours, `palette-exhausted` is returned naming the first blocked faction in faction order (FR-644 defensive guard).
- **Device `maxTextureSize` smaller than `entries + 1` (e.g. a 3,000-entry / 3,000-faction map on a 2,048-max GPU):** passes `checkCounts` (≤ 65,535), then cleanly refused by `checkCapabilities` (`texture-too-small`) naming the required size.
- **Round changes and later-round absorptions:** faction colours never change between rounds; faction indices ≥ 256 absorb and are absorbed with borders becoming territory lines identically to indices ≤ 255.

## Out of scope
- Raising the 65,535 territory-entry ceiling or packing lookup textures / tiling the id image for devices whose `maxTextureSize` is smaller than the map or table width (follow-up V3).
- HUD/UI redesign for browsing or searching thousands of factions in the sidebar, leaderboard, or Discord embeds (separate UX work if needed).
- Label layout performance overhaul at thousands of factions (existing incremental per-step layout stays untouched; load timing on `world-1815-4` is measured and recorded).
- Any change to `packages/shared`, `packages/sim`, `packages/protocol`, `apps/server`, `apps/bot`, map validation, or the map package format.
