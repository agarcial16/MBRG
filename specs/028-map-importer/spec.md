# Spec 028 — Map importer (vector route)
Status: approved (2026-11-21, by the user via the orchestrator: vector route first, painted later; amended the same day with the user's answers to OQ5 and OQ6, and with the inset-recentring amendment PD6)
Tier: Full SDD (a new map source: whatever it writes is read by the server's map checks and the viewer, and a bad package halts matches). Depends on 001/002 (map format, validation, sea zones, land + sea connectivity), 003a (presentation data, id image values, contact adjacency, names, colours), 003b (projection, centre-point rasterization, sea seeds, piece cleanup, self-check, atomic write, report, preview, extraction step, libraries), 003c (enclosed water, amended cleanup), 004 (viewer package checks, capability check, faction colours) and 008 (map list, map digest). Ids: FR-586 to FR-614, NFR-132 to NFR-138.

Answers of 2026-11-21 (user, via orchestrator; the first two different from the draft's recommendation):
- OQ5 ANSWERED: **no design cap on the image side**. The importer accepts what the source needs; only resource guards remain (file sizes, feature and position counts, and an absolute pixel bound stated as memory: W × H at most 2^28 pixels, FR-600). Whether a device can draw a map is the **viewer's** question, not the importer's: the viewer must refuse gracefully a map it cannot draw (named follow-up V1). Texture tiling or polygon-mesh rendering for huge maps on weak devices is recorded as a future viewer option (follow-up V3), out of scope here; nothing in this spec ties the package to today's renderer.
- OQ6 ANSWERED: **faction owners up to 9,999**. (a) The importer accepts up to 9,999 owning factions (FR-607). (b) Today's viewer does not draw more than 255 factions (one-byte owner table) and colours them from a 12-colour palette (004 FR-141): a procedural palette and a wider owner table are the named follow-up V2, and the importer only reports these limits as warnings. A map whose factions are its 8,132 municipalities means a match of 8,131 rounds: it is the package-level **stress proof** of the pipeline (FR-614), not necessarily a weekly match. The 120-second bound of NFR-136 is unchanged.
- PD6 ANSWERED: **insets re-centre**. FR-600's fixed 0° central meridian applies to the main map only; each inset keeps its own central meridian (FR-601). The amendment also fixes the wrap: a view with central meridian lon0 projects every longitude as `lon − lon0` wrapped into (−180, 180], and `antimeridian-edge` is judged per view against that lon0, so an unsplit antimeridian ring that fails the main map (lon0 = 0°) can import inside an inset centred on it.

This draft assumes the recommended answer of each other open question (GeoJSON as the import contract with shapefiles through the generalised extraction step, a hand-edited curation file with rules by column, a 120-second bound at the scale fixture, no per-collection notes for historical sources, insets, Lambert plus Equal Earth in a square frame, seeds plus sea units, optional gap filling, the dev map equivalence proof, and units merged by key). A different answer changes the requirements that name that question.

## Context and goal
The roadmap's next feature is the map importer. The user's map wishlist is overwhelmingly real-world: Spain by provinces; **Spain by municipalities (8,132 units, the founding goal of the project, impossible by hand)**; the world; concrete regions (the Caribbean, a continent, a selection of countries); the world carved as desired; historical maps (1035, 1444, 1914, 1939, the Cold War, the Roman world); alternate history on real data; and, last, painted or fantasy maps. The user decided (2026-11-21) that both import routes will exist, and that the **vector route comes first**: real-world polygons with properties in, map package out. The painted-image route (route A: a flat-colour PNG plus a legend, and any pixel editor) becomes a later spec.

The ground already exists. Spec 003b built the dev map from Natural Earth shapefiles through its own pipeline: an extraction step (shapefile and DBF reading, NUL-padded text), Lambert azimuthal equal-area projection into a square frame, centre-point rasterization, sea seeds, piece cleanup, adjacency from 4-connected pixel contact, a self-check and an atomic write; its libraries were approved for exactly those areas, and it named "later importers: the builder pipeline as a reference". Running it today on the committed inputs rebuilds `maps/dev` byte for byte (2,048 × 2,048, 5 factions, 70 land territories, 17 sea zones, 116,294 source positions, about 1.2 km per pixel side, about 7 seconds on the development machine, measured 2026-11-21). What 003b hard-wires is the source: Natural Earth fields (`adm0_a3`, `adm1_code`, `name_es`), one faction per country, a grouping table keyed by province codes.

This spec **generalises that pipeline from "Natural Earth only" to "any GeoJSON source of polygonal units with properties"**: the operator says which property is the unit key and which the name, selects a subset (a box, a property match, a date range), and curates in two layers: per unit (name, land or sea, owner) and by grouping (units merged into one territory, territories assigned to factions, by column rules or one by one). That curation file is the "editor" of real-world maps. Its output is an ordinary map package that the server lists (008) and the viewer draws (004) with no change to either, as long as the package is within today's viewer limits (the report lists any it exceeds, FR-607). What a valid package is stays exactly what 001 to 004 say; the 24-bit id image and the 4-connected adjacency rule are untouched.

### Scale budget of the founding goal (the numbers behind NFR-136)
- Spain has 8,132 municipalities with a mean area of 62.1 km²; 220 have 5 km² or less and 557 between 5 and 10 km² (Ministry of Agriculture statistical yearbook 2025, table 1.2, from the National Geographic Institute). The smallest, Emperador (about 0.03 km²), is an enclave inside another municipality.
- The mainland plus the Balearic Islands span about 13.6° of longitude by 7.9° of latitude, about 1,164 × 878 km; with the 2% margin of 003b the square frame is about 1,210 km a side.
- At a side of 4,096 pixels a pixel is about 0.295 km a side, 0.087 km² in area: the mean municipality is about 710 pixels, a 5 km² one about 57 pixels; S = 40 pixels means 3.5 km², S = 8 means 0.7 km². At a side of 2,048 a pixel is 0.35 km² and S = 40 means 14 km², so every one of the 777 municipalities of 10 km² or less would fall below it.
- The Canary Islands (88 municipalities) lie about 1,000 km south-west: in one frame with the mainland the side grows to about 2,300 km and every pixel covers about 3.6 times more ground. Hence insets (FR-601, OQ7).
- At the largest side the pixel guard allows (16,384, FR-600) a pixel is about 0.074 km a side, 0.0055 km²: the mean municipality is about 11,400 pixels and Emperador about 5. Even there S = 8 does not give every municipality a piece: the import lists every territory below S at once (FR-604) and the curation merges them or the operator lowers S.
- 8,132 land territories plus 59 sea zones are 8,191 entries. Today's viewer keeps its per-entry tables entries + 1 texels wide (its capability check of 004 FR-135, as built), so it needs a maximum texture size of at least max(W, H, entries + 1): 8,192 for this map at side 4,096, 16,384 at side 16,384 (WebGL 2 guarantees only 2,048). That is a device question the importer no longer answers (OQ5): it prints the size, and the viewer refuses what it cannot draw (follow-up V1).
- Factions: the importer accepts up to 9,999 (OQ6). Today's viewer draws at most 255 (one-byte owner table) from a 12-colour palette reused between factions that are not direct candidates of each other (004 FR-141). Spain by municipalities is drawable today with its 52 provinces or 19 autonomous communities and cities as factions. With one faction per municipality (8,132 factions) the package imports and validates (FR-614) but needs follow-up V2 to be drawn, and a match removes one faction per round, so it lasts **8,131 rounds** (the dev map: 4); even at one round a minute that is about five and a half days. It is the stress proof of the pipeline, not a weekly match.

## Users
- **Operator**: curates the maps a server offers (`MBRG_MAPS`, 008); imports real-world sources and must trust that a package is valid before listing it.
- **Map author** (often the operator): carves real geography into territories and factions without writing coordinates, links or 8,132 lines by hand.
- **Spectator / predictor** (indirect): sees recognisable named territories and factions, and borders that match what is drawn.

## User stories
- US-1. As a map author, I want to point the importer at a GeoJSON file and name its key and name columns, so that any real-world source becomes a map without a source-specific builder.
- US-2. As a map author, I want to select a subset of a source (a box, a property value, a date range), so that I can make Spain from a world file, the Caribbean, or the world of 1914.
- US-3. As a map author, I want to merge units into territories and assign them to factions by column rules and by per-unit exceptions, so that 8,132 municipalities become any carve I want in a reviewable file.
- US-4. As a map author, I want every problem of my source and my curation reported in one run, with the units it names, so that I can fix them all at once.
- US-5. As an operator, I want an imported package to pass the same checks as the dev map and the viewer's limits, so that listing it can never halt a match or break the viewer.
- US-6. As an operator, I want the importer to never overwrite a package and to work on 8,132 units in bounded time, so that Spain by municipalities is a routine import.

## Definitions
- **Source**: a GeoJSON file of features read by the importer (FR-587). The **primary source** gives the units; a **context source** gives only other land (FR-589).
- **Feature**, **property**: a GeoJSON feature and a member of its `properties` object. A property value is **present** as in 003b (an own member whose value is a non-empty text); a **usable value** is a text value or an integer number, an integer being read as its shortest decimal text (`28`, not `28.0`).
- **Unit**: all features of the primary source that share one key value (FR-593): one place of the source (a municipality, a province, a country), possibly made of several features.
- **Curation file**: the JSON file the map author writes (FR-592); it is an importer input, never part of the map package. It holds the column mapping, the selection, the parameters, the per-unit layer and the grouping layer.
- **Selected unit**: a unit kept by the selection (FR-594). Every other unit of the primary source, every excluded unit and every context feature is **other land** (drawn as background, never water, 003b).
- **Territory key**, **faction key**: text of 1 to 256 code units naming a territory or a faction in the curation; generated keys are property values.
- **Inset**: a group of selected units drawn with their own projection centre, at the main scale, in a pixel rectangle of the image (FR-601).
- **Water pixel**, **frame**, **S** (minimum piece size), **piece**, **map order**, **contact count**, **enclosed water set**: as in 003b and 003c.
- **Required texture size**: max(W, H, entries + 1), the texture size today's viewer needs to draw the map (004 FR-135 as built); reported, never a gate (FR-607).
- **Caps**: the limits of FR-588, FR-592, FR-600 and FR-607. Each is a resource guard or a format rule; none is a device or renderer limit (OQ5).
- **Viewer limits**: what today's viewer (004) can draw: a required texture size within the device's, at most 65,535 entries (two-byte entry index), at most 255 factions (one-byte owner table), and a colour assignment that does not fail (004 FR-141). The importer reports them (FR-607); the viewer enforces them (follow-ups V1 to V3).

## Functional requirements
### Where it runs (OQ1)
- FR-586: THE importer SHALL be an offline command of the existing map builder tool (003b), run by the operator or a map author on local files, with three modes: **extract** (shapefile to source, FR-590), **inspect** (source to summary and draft curation, FR-591) and **import** (sources and curation to map package). It SHALL NOT open a network connection, and neither the server nor the viewer SHALL run it, call it or accept an upload. Exit status, usage errors and error output SHALL follow 003b (0 success, 1 failure, 2 usage error; one JSON object per error per line on standard error with an English `kind`). The existing build command, its inputs and its report SHALL stay unchanged (NFR-132).

### Input contract
- FR-587: THE importer SHALL accept as a source only a UTF-8 JSON file holding a GeoJSON `FeatureCollection` whose features have a `properties` object (or `null`, read as an empty object) and a geometry of type `Polygon` or `MultiPolygon`, coordinates `[longitude, latitude]` in degrees (positions with a third or later number are read on their first two). A feature with a `null` geometry SHALL be skipped and counted in the report; any other geometry type SHALL fail with `unsupported-geometry` (feature index, type). IF the collection has a `crs` member naming anything other than `urn:ogc:def:crs:OGC:1.3:CRS84`, `EPSG:4326` or `EPSG:4258`, THEN `unsupported-crs`; IF any longitude is outside −180 to 180 or any latitude outside −90 to 90, THEN `coordinates-not-degrees` (first feature index), so that a projected source (for example UTM metres) is refused and never reprojected. Containment of points by rings and polygons SHALL be exactly the rules of 003b FR-115 (even-odd per ring, holes, union of overlapping polygons, boundary inside, zero-area rings ignored); the importer SHALL never simplify, clip or repair geometry.
- FR-588: THE importer SHALL check before parsing that each source file is at most 256 MiB, and while reading that the sources together hold at most 100,000 features and 20,000,000 positions, each feature at most 256 properties, and each property value it uses (FR-593 to FR-597) at most 1,024 code units; IF a cap is exceeded, THEN `source-too-large` (file, cap, value found) and the read stops.
- FR-589: THE curation MAY name up to 8 context sources; their features (any properties, same geometry rules) SHALL be drawn only as other land, so that neighbours outside the selection (France and Portugal around Spain) are never water. Context polygons are never units and never selected.
- FR-590: THE extract mode SHALL generalise the extraction step of 003b FR-131 to any shapefile: given a `.shp`, its `.dbf`, an optional `.cpg` and `.prj`, and a list of property names to keep (all when none is given), it SHALL write a source (FR-587) with one feature per shapefile record, in record order, holding only those properties. Text values SHALL be decoded with the encoding named by the `.cpg` file or by the command (UTF-8, Windows-1252 or ISO-8859-1); IF neither names one, THEN `unknown-dbf-encoding`; IF a kept property name is not a DBF field, THEN `unknown-field`. Trailing space and NUL padding of DBF text SHALL be removed (decoding, 003b FR-131) and an empty DBF text becomes `null`; nothing else of a value is changed. IF a `.prj` file is given and declares a projected coordinate system (its text starts with `PROJCS`), THEN `projected-crs`. Coordinates SHALL be kept as read unless the command asks for rounding to a fixed number of decimal places of at least 6. Two runs on the same files SHALL give byte-identical output.
- FR-591: WHEN the inspect mode reads a source that passes FR-587 and FR-588, THE importer SHALL print a deterministic summary: feature count, skipped null geometries, position count, longitude and latitude range; and for each property name, in order of first appearance: the number of features having it, the value types seen, the number of distinct usable values, whether those values are unique over the features (a key candidate), and the first 5 distinct values. WHEN asked, it SHALL also write a draft curation file (never inside a package folder) with every member of FR-592 present, an empty `columns.key`, empty lists and default parameters, so that an unedited draft always fails import with `invalid-curation`. The same source SHALL always give the same summary and draft, byte for byte.

### Column mapping and units (OQ12)
- FR-592: THE curation file SHALL be a JSON object of at most 16 MiB with exactly these members (optional ones may be absent): `primary` (path of the primary source, relative to the curation file); optional `context` (list of paths, FR-589); `columns` (`key`: one property name; `name`: a list of 1 to 3 property names); optional `select` (list of filters) and `exclude` (list of unit keys) (FR-594); `params` (FR-600); optional `units` (FR-595); optional `territoryBy`, `territoryNames` (FR-596); optional `factions` (at most 9,999 entries), `factionBy` (FR-597); optional `seas` (at most 1,024 entries, FR-598); optional `insets` (FR-601). Unknown members, wrong types, an empty `key` or a list over its length SHALL fail with `invalid-curation` (member path).
- FR-593: THE importer SHALL give each feature of the primary source the usable value of its `columns.key` property as its key (`missing-unit-key` when absent, `invalid-unit-key` when not usable: feature index) and SHALL form one unit per distinct key, made of the union of its features' polygons, in order of first feature. A unit's name SHALL be the value of the first property of `columns.name` that is present on its first feature, used exactly as given (never trimmed or normalised, 003b FR-121); IF two features of one unit have different names, or different usable values of a property used by a filter or a rule (FR-594, FR-596, FR-597), THEN `conflicting-unit-property` (unit key, property).

### Selection
- FR-594: THE importer SHALL select the units that match every filter of `select` (all units when it is empty or absent) and are not in `exclude`. A filter is either `{ property, eq }`, `{ property, in }`, `{ property, gte }` or `{ property, lte }` on the unit's usable value (two integers compare as numbers, two texts by code units, a text and an integer never match, an absent value never matches; so ISO dates written as text compare as dates), or `{ bbox: [west, south, east, north], mode }` with `mode` `within` (the unit's longitude and latitude range lies inside the box) or `intersects` (the ranges overlap). IF no unit is selected, THEN `empty-selection`; IF `exclude`, `units` or a curation entry names a key that is no unit, THEN `unknown-unit` (key).

### Curation layer 1: per unit
- FR-595: THE `units` member SHALL map a unit key to an object with optional `name` (replaces the unit's name, FR-593), `kind` (`land`, the default; `sea`; or `exclude`, same as listing it in `exclude`), `territory` (a territory key) and `faction` (a faction key). A per-unit value SHALL take precedence over every rule of FR-596 and FR-597. A `sea` unit SHALL NOT name a faction (`sea-with-faction`).

### Curation layer 2: grouping (OQ2)
- FR-596: THE importer SHALL give every selected unit a territory: its `units` entry's `territory` when given; else, WHERE `territoryBy` (`{ property, nameProperty? }`) is given, the unit's usable value of `property` (`missing-group-value` when absent); else a territory of its own, keyed by its unit key. Units with the same territory key form one territory (merged; their pixels are one entry). A territory's name SHALL be, in this order: `territoryNames[key]`; else, for a key from `territoryBy` with a `nameProperty`, that property's value, which every unit of the territory must share (`conflicting-group-name`); else, for a territory of one unit, the unit's name; else none, and the import fails with `missing-territory-name`. A territory made of land and sea units SHALL fail with `mixed-territory-kind`.
- FR-597: THE importer SHALL give every land territory exactly one faction: the faction of its units, each taken from its `units` entry's `faction` when given, else WHERE `factionBy` (`{ property, nameProperty? }`) is given from that property's value; IF a land unit gets none, THEN `missing-faction`; IF the units of one territory get different factions, THEN `split-territory-faction` (territory key, the faction keys). Factions SHALL be the `factions` list (`{ key, name, color? }`, names and colours as 003a FR-87 and FR-88) followed by every other faction key used, generated in code-unit order of key, named by `nameProperty` (shared by all its units, `conflicting-group-name`) or else `missing-faction-name`. A listed faction that no land territory uses SHALL fail with `faction-without-territory`. A faction's territories need not touch (as in the dev map); the report lists every faction whose territories form more than one group over land links.
- FR-598: THE importer SHALL make one sea zone per sea territory (FR-595, FR-596) and one per entry of `seas` (`{ name, lon, lat }`, a sea zone seed of 003b FR-116 with its errors `seed-outside-frame`, `seed-not-water` and `duplicate-seed-pixel`). Zero sea zones are allowed. Water pixels SHALL be assigned by 003b FR-116 and 003c FR-162 to FR-164 with the pixels of every sea zone (its seed pixel, or its rasterised sea units) as sources, ties to the zone first in map order; WHEN there is no sea zone, every water pixel becomes background.
- FR-599: IF the curation breaks FR-592 to FR-598, THEN THE importer SHALL report every problem, ordered by kind in this order and, within a kind, by the code-unit order of the first data field: `invalid-curation`, `missing-unit-key`, `invalid-unit-key`, `conflicting-unit-property`, `unknown-unit`, `empty-selection`, `invalid-name`, `invalid-color`, `invalid-key` (a territory or faction key that is not 1 to 256 code units), `duplicate-faction-key`, `sea-with-faction`, `missing-group-value`, `mixed-territory-kind`, `conflicting-group-name`, `missing-territory-name`, `missing-faction`, `split-territory-faction`, `missing-faction-name`, `faction-without-territory`, `too-many-factions` (FR-607); each once per distinct data (as 003b FR-113). Repeated faction names or colours are reported by the presentation check (FR-606).

### Projection and frame (OQ7, OQ8)
- FR-600: THE `params` member SHALL hold `side` (W = H, an integer 64 to 16,384), `margin` (a number 0 to 0.5), `minPieceSize` (S, an integer 1 to 10,000), `projection` (`laea` or `equal-earth`) and optional `gapFill` (FR-603). The side bound is a resource guard, not a design limit (OQ5): W × H stays at most 2^28 = 268,435,456 pixels, so the largest per-pixel buffer of the import (4 bytes a pixel) stays at most 1 GiB; no requirement of the importer reads a device's texture size. WITH `laea`, THE importer SHALL project and frame exactly as 003b FR-114, the selected land units outside every inset taking the place of the non-excluded source provinces; IF a vertex of a selected land unit lies more than 90° of great-circle arc from the projection centre, THEN `selection-too-wide` (unit key); a context or other-land polygon with any vertex beyond 90° SHALL be ignored. WITH `equal-earth`, THE importer SHALL use the Equal Earth projection on the sphere with central meridian 0° **for the main map only** (each inset has its own, FR-601, PD6) and the same square frame rule; IF an edge of a polygon used in a view has two ends whose longitudes, each wrapped as `lon − lon0` into (−180, 180] with lon0 the view's own central meridian, differ by more than 180°, THEN `antimeridian-edge` (unit key or context file and feature index) — with lon0 = 0° on the main map, exactly the rule as drafted.
- FR-601: EACH entry of `insets` (`{ select, at: [x, y] }`) SHALL take the selected units that match its filters (a unit in two insets: `unit-in-two-insets`; none: `empty-inset`) and draw them with the map's projection centred on the midpoint of their own longitude and latitude ranges (with `equal-earth` that midpoint longitude is the inset's own central meridian lon0, its longitudes wrapped as FR-600 says, PD6), at the main frame's pixel side, in the rectangle of their projected bounding box expanded by margin × main frame side on each side, rounded outward to whole pixels, placed with its top-left pixel at (x, y). Pixels inside an inset rectangle SHALL be assigned only from that inset's projection (its units, other land and context features, water), pixels outside every rectangle only from the main projection. IF a rectangle leaves the image, overlaps another, or covers a pixel that the main projection gives to a selected land unit, THEN `inset-outside-image`, `insets-overlap` or `inset-hides-land`. A seed lies in the first inset whose projection puts it inside that inset's rectangle, else in the main projection.

### Pixels, cleanup and adjacency
- FR-602: THE importer SHALL assign every pixel by its centre (003b FR-115) to the territory whose units contain it (first in map order when several do), else to background when other land contains it, else to water (FR-598). It SHALL never blend values or use partial coverage.
- FR-603: WHERE `gapFill` G (an integer 1 to 10,000) is given, THE importer SHALL give each enclosed water set (003c) of fewer than G pixels that touches a land territory, as a whole, to the land territory with the highest contact count with it (ties to the first in map order), before 003c FR-162 runs; the report lists every filled set. Without `gapFill` no water becomes land, as in 003b.
- FR-604: WHEN pixels are assigned, IF any land territory or sea territory has no piece of S pixels or more, THEN THE importer SHALL fail with one `territory-below-min-size` per such territory (key, name, its pixel count, its largest piece), all reported in map order before any cleanup; otherwise it SHALL apply the piece cleanup of 003b FR-117 as amended by 003c FR-163, including `vanished-entry`.
- FR-605: THE importer SHALL derive every link only from pixel contact (003a FR-108, 003b FR-118), with no field for links; number factions 1..K in faction order (FR-597), land territories 1..L grouped by faction in faction order and, inside a faction, in code-unit order of territory key, then sea zones: sea territories in code-unit order of key, then seeds in list order; and write the presentation data with faction names and colours and every entry's name (003b FR-121, FR-125 formatting). Ids SHALL stay within 1..16,777,215 (003a) and every value of the id image is the entry's id (003a FR-106).

### Package gate (salvaged from the first draft)
- FR-606: THE importer SHALL run the self-check of 003b FR-122 on the final map, presentation data, id image values and encoded PNG; any error it reports (including `too-few-factions`, `disconnected-map`, `invalid-name`, `duplicate-color`) SHALL fail the import as reported.
- FR-607: THE importer SHALL refuse a package only on its own caps, never on a viewer limit (OQ5, OQ6 answered): IF the curation gives land territories more than 9,999 factions, THEN `too-many-factions` (cap, count), found with the curation checks (FR-599) before any pixel buffer is allocated. Entries need no cap of their own: they are at most the units (at most 100,000, FR-588) plus the seeds (at most 1,024, FR-592), far below the 16,777,215 ids of 003a. THE report SHALL print a viewer-limits section: the required texture size, and, as warnings that never fail the import, each viewer limit the package exceeds: a required texture size above 2,048 (the size WebGL 2 guarantees; a smaller device gets the 004 FR-135 message), more than 65,535 entries, more than 255 factions, and the first faction for which the colour assignment of 004 FR-141 would fail (`palette-exhausted`, computed by the same shared function as the viewer, NFR-132).
- FR-608: THE import SHALL check, in this order, stopping after the first stage with errors and reporting every error of that stage: usage; output folder; curation file; sources; column mapping, selection and curation (FR-599); projection and insets; pixel steps (FR-598, FR-604, cleanup); self-check (FR-606). Viewer limits are only reported (FR-607). IF any check fails, THEN THE importer SHALL create, modify or delete no file in the output folder. IF the output folder exists and is not empty, THEN `output-not-empty` before any input is read, so that a listed package is never replaced (a changed package halts its running matches, 008). A successful import SHALL write `map.json`, `presentation.json` and `ids.png` as the builder writes them (003b FR-105, FR-125) with the temporary-file and rename rules of 003b FR-123.

### Report, preview and inspection aids
- FR-609: WHEN an import succeeds, THE importer SHALL print a deterministic report with English labels: the SHA-256 of the curation file and of each source; features read and null geometries skipped; units, selected units and units made of several features; projection, centre, frame and each inset rectangle; the pixel side in kilometres (sphere of radius 6,371 km, at the projection centre); counts of factions, land territories, multi-unit territories and sea zones; the viewer-limits section (FR-607); the smallest piece; every reassigned piece; every gap-filled set; enclosed water (003c FR-165); every entry with more than one piece; and every faction split over land (FR-597).
- FR-610: WHEN asked, THE importer SHALL write a preview image outside the output folder as 003b FR-126 does (a path inside it is a usage error); WHEN an import fails at or after the pixel steps, it SHALL still write the preview of the last assignment it computed.

### Proofs and integration (OQ11)
- FR-611: THE repository SHALL hold a curation file that expresses the dev map's inputs (the committed Natural Earth provinces as primary source, the committed other land as context, the grouping as per-unit territories, the five factions listed in `adm0_a3` order with their names, the excluded provinces, the sea seeds and the dev parameters); a test SHALL import it and find `map.json` and `presentation.json` byte-identical to `maps/dev` and `ids.png` decoding to the same pixel values (003b FR-130). This proves the generalisation reproduces the 003b pipeline.
- FR-612: THE repository SHALL hold a small committed sample (a synthetic GeoJSON primary source of at most 200 KB, a context source, a curation file and the expected package) exercising: a unit made of two features, a `territoryBy` merge, a `factionBy` assignment with a per-unit exception, a `sea` unit and a seed, a lake, an inset, a gap fill, an excluded unit and a date-range filter; a test SHALL import it and compare the three files byte for byte. The sample SHALL NOT be added to `maps/`, the server settings or the e2e harness (023).
- FR-613: THE deployment guide SHALL gain the operator steps: extract (when the source is a shapefile), inspect, write the curation, import with a preview, review report and preview, add the folder to `MBRG_MAPS` with an absolute path (and optionally `MBRG_PUBLIC_MAPS`); the reprojection or simplification of a source with outside tools before import; how to read the viewer-limits section (FR-607): a required texture size above 2,048 leaves out devices with less, and a package over 255 factions or 65,535 entries is not drawable by today's viewer (it stops with an internal error, not a message, until follow-up V1), so it is not listed until V1 and V2 ship; and the reminder that a source's licence travels with every map built from it.
- FR-614: THE repository SHALL hold the **stress proof** of the pipeline (OQ6 answer), a package-level check run by the opt-in command of NFR-136: the scale fixture of NFR-136 imported with **one faction per land unit (8,132 factions, 8,132 land territories, 59 sea zones)** SHALL succeed; the written package SHALL load through the server's map list (008: the map validation of 001/002 and the map digest) and pass the presentation and id image checks of 003a that the viewer runs before drawing (004 FR-133); and its report SHALL show the viewer-limit warnings for more than 255 factions and, when it fails, the colour assignment. Its time and peak memory are recorded, not bounded. It proves import, validation and packaging at that scale; it draws nothing and plays no match (a match on it lasts 8,131 rounds). Inside `npm test`, a small test SHALL import 300 single-unit factions (no 255 cap, warning shown) and a curation of 10,000 factions SHALL fail with `too-many-factions` before any pixel buffer is allocated.

## Non-functional requirements
- NFR-132 (Compatibility): the map format, presentation format, id image and PNG formats, `MatchState`, the protocol, the server, the viewer, the bot and the sim do not change; `maps/dev` and every golden stay byte for byte; the build command, its inputs, its report and its rebuild test stay unchanged. A builder function the importer shares (projection, rasterization, sea, cleanup, adjacency, self-check, write, preview, the colour assignment of 004 FR-141) may be moved or generalised only with unchanged behaviour, proven by the existing tests passing unedited and by FR-611.
- NFR-133 (Dependencies): no new dependency. The PNG library approved in 003b is used within the builder tool; the shapefile library stays used only by the extraction step (003b NFR-20, generalised by FR-590); Equal Earth and every geometry step are own code. The manifest pin test of 003b NFR-20 stays unchanged.
- NFR-134 (Purity and determinism): the inspect, extract (after file reading) and import cores take bytes in and give bytes out, with the PNG codec injected; no file system, clock, randomness or network inside them (003b NFR-14, same `node:zlib` exemption). Verified by running each core twice on the same inputs with byte-identical outputs and by the purity scan extended to the importer sources.
- NFR-135 (Input safety): every size cap is checked before the work it bounds: a 300 MiB source fails with `source-too-large` before parsing; a curation file over 16 MiB fails before parsing; a curation asking for a side of 16,385 (or 100,000) fails with `invalid-curation` before any pixel buffer is allocated; a curation giving 10,000 factions fails with `too-many-factions` before any pixel buffer is allocated.
- NFR-136 (Scale, named: Spain by municipalities): an import of a generated scale fixture with **8,132 land units in 52 factions, 59 sea zones (8,191 entries), at least 5,000,000 positions, a side of 4,096, S = 8, one inset and a context source** completes within **120 seconds** from reading the source bytes to the three artifacts written, within the runtime's default heap limit, on the development machine run alone; the inspect mode on the same source completes within 30 seconds. These numbers stand after the OQ5 and OQ6 answers: the fixture is within every guard (side 4,096 of at most 16,384; 52 factions of at most 9,999; under 100,000 features and 20,000,000 positions), and larger sides (16 times the pixels at 16,384) and the stress proof of FR-614 are recorded, not bounded. The test runs as an opt-in command outside `npm test`; the plan measures it on a prototype first and confirms these thresholds or proposes others through a change of this spec (as 003b NFR-16). The suite keeps a smaller scale test (1,000 units at side 2,048) inside `npm test` with an explicit timeout.
- NFR-137 (Language): code, identifiers, error kinds, report labels and docs in English; no UI strings are added. Names in sources and curation are the author's content and are never translated.
- NFR-138 (Testability): tests first for every id; fixtures mimic real sources: a unit split over several features with the same code (official municipal "recintos"), a Windows-1252 DBF with a `.cpg`, a DBF without one, a `.prj` in UTM, NUL-padded text, integer codes, a feature with `null` geometry, overlapping and gapped polygons (historical collections), a property present on only some features, a world source split at the antimeridian; the traceability ledger is extended with FR-586 to FR-614 and NFR-132 to NFR-138.

## Edge cases
- A source in projected metres (UTM): `coordinates-not-degrees` (or `projected-crs` at extraction); the author reprojects outside (FR-613).
- An official municipal file with one feature per enclave part: one unit per code with several polygons (FR-593); its name must agree across parts.
- Integer codes that lost their leading zeros (`8019` for `08019`): keys and filters compare the decimal text, so `eq: "08019"` matches nothing; the inspect summary shows the values as stored.
- A municipality smaller than one pixel (Emperador): no pixel or a tiny piece, `territory-below-min-size` lists it with every other such unit in one run; the curation merges it (`units.<key>.territory`) or S is lowered.
- 8,132 territories each its own faction: imports (the stress proof, FR-614); the report warns that today's viewer cannot draw it (more than 255 factions; and any sea zone touched by more than 12 coastal factions makes them direct candidates of each other, so `palette-exhausted`, 004 FR-141); a match on it would last 8,131 rounds. 10,000 factions: `too-many-factions`.
- A side of 16,384 (the pixel guard): accepted, untimed; the required texture size is 16,384, so most phones and many laptops cannot draw it today (follow-ups V1, V3). A side of 16,385: `invalid-curation`.
- A world source of 45,000 second-level units, each its own territory: imports (under 100,000 features); more than 65,535 entries is a viewer-limit warning, not an import error.
- Spain from a world-countries file: France and Portugal are unselected units, hence other land; from a Spain-only file the same needs a context source, or the Pyrenees border becomes coast.
- The Canary Islands without an inset: same frame, about 3.6 times the ground per pixel; with an inset placed over the Atlantic part of the frame: its water touches the main water and joins its zone unless a seed lies inside the inset.
- A historical collection with overlapping polygons: the territory first in map order wins each overlapped pixel (FR-602); gaps between polygons become water, joined to a sea zone (003c) unless `gapFill` gives small enclosed gaps to the land around them.
- A historical collection with unnamed polygons: `missing-territory-name` for each, unless `territoryNames` or a `units` name gives one, or the polygon is excluded.
- A date-ranged collection (one feature per country and period): a `lte`/`gte` pair on ISO date texts selects the map of a given day; two periods of one country selected at once share a key and fail `conflicting-unit-property` if their properties differ.
- A selection spanning more than a hemisphere with `laea`: `selection-too-wide`; `equal-earth` draws it.
- A world source not split at the antimeridian (Fiji, Chukotka): `antimeridian-edge` with `equal-earth`.
- A narrow strait closing at the chosen side: a land link, visible in the preview, accepted as built (no hand links, 003b).
- An unedited draft curation: `invalid-curation` for the empty key.
- Re-importing a corrected map: a new output folder; reusing a listed folder is refused (FR-608).
- A package that imports but that a phone cannot draw (required texture size 8,192 on a device limited to 4,096): the import succeeds, since the importer reads no device size (OQ5); the report printed the required size; the viewer shows its capability message (004 FR-135).

## Out of scope
- **Route A, the painted-image importer** (a flat-colour PNG plus a legend: colour scan, exact colour matching, an optional border colour grown into the nearest entries, a draft legend) **and any visual or pixel editor**: a later spec, which reuses the curation file's faction and naming members and the package gate of this spec.
- An in-browser importer page and any server upload route; fetching sources from the network.
- Reprojection from projected coordinate systems, geometry simplification or repair, and any source format other than GeoJSON (directly) and shapefile (through extraction): TopoJSON, GeoPackage, KML, Azgaar.
- More than 9,999 factions; non-square images; projections other than Lambert azimuthal equal-area and Equal Earth (main-map central meridian 0°; insets re-centre their own, FR-601).
- Any viewer, server, bot or protocol change, including viewer performance work at 8,132 territories (measured in the hand run, a later spec if needed) and the follow-ups below; playing a match with thousands of factions (8,131 rounds: server timing, predictions, bot); a map title; a background art layer.

### Named follow-ups (recorded on `docs/board.md` by the feature PR, so they are not lost)
- **V1, viewer: graceful refusal of a map it cannot draw.** Today the viewer refuses with a Spanish message a texture size above the device's (004 FR-135) and a failed colour assignment (004 FR-141), but stops with an internal error above 65,535 entries or 255 factions. V1 makes every viewer limit a Spanish message that names what the map needs and what the device or viewer offers (for example "this map needs a texture of 16,384; this device offers 8,192"), drawing nothing, before any operator lists a package with a viewer-limit warning.
- **V2, viewer: many factions.** A wider owner table and a deterministic procedural palette, computed from the map and presentation data only, so that up to 9,999 factions get distinct colours where they touch; plus what the faction names, labels, legend and leaderboard do at thousands of factions. Whether a match of thousands of rounds is ever offered (server timing, predictions, bot) is a separate product question, not part of V2.
- **V3, viewer: huge maps on weak devices (a future option).** Texture tiling of the id image and per-entry tables, or rendering territories as polygon meshes, so that a map larger than a device's texture size can still be drawn. The package format (`map.json`, `presentation.json`, the 24-bit `ids.png`) is input enough for either; this spec adds no requirement that reads a device size or the viewer's table layout, so it does not lock the format to today's renderer.
- Listing a map automatically in the server settings; committing a large real-world map under `maps/`; committing licensed sources.

## Open questions
- [NEEDS CLARIFICATION] OQ1. Shapefile support, or GeoJSON only? **A (recommended):** GeoJSON is the import contract; shapefiles enter through the extraction step generalised to any shapefile (FR-590): it keeps the DBF lessons (padding, encodings, `.cpg`, `.prj`) and keeps the shapefile library where 003b NFR-20 allowed it. **B:** the import reads shapefiles directly: one step fewer, but the unmaintained shapefile library enters the import path (an NFR-20 change, ask first). **C:** GeoJSON only, operators convert with outside tools: loses the DBF lessons and the deterministic, tested conversion.
- [NEEDS CLARIFICATION] OQ2. The curation file format? **A (recommended):** one hand-edited JSON file with column rules (`territoryBy`, `factionBy`) and per-unit exceptions, a draft written by inspect, every error in one run: reviewable, diffable, repeatable, and 8,132 units need only a few lines when a column already holds the grouping. **B:** a guided command-line dialogue: friendlier the first time, but not reviewable or repeatable, and still needs a file behind it. **C:** A plus a per-unit CSV (unit, territory, faction) for spreadsheet editing: a later addition if rules prove insufficient.
- [NEEDS CLARIFICATION] OQ3. The time bound at 8,132 units? **A (recommended):** 120 s for the scale fixture of NFR-136 (4 times the dev map's pixels, about 40 times its positions, 116 times its land territories), measured on a prototype in the plan and confirmed or changed then; opt-in command, a 1,000-unit test in `npm test`. **B:** 60 s as 003b NFR-16: likely too tight at 16.8 million pixels in plain JavaScript. **C:** no bound, report only: a slow regression would pass unseen.
- [NEEDS CLARIFICATION] OQ4. Do historical sources (1914, 1444-style collections) need their own acceptance notes? **A (recommended):** no per-collection requirements: the generic tools cover their quirks (date-range filters, `null` geometries skipped, overlaps first in map order, `gapFill`, names given in the curation), backed by edge cases, fixtures that mimic them (NFR-138) and hand run 2 on a collection the user picks; licences stay the operator's duty (FR-613). **B:** one acceptance note per named collection: ties the spec to third-party files whose versions and licences change.
- OQ5 and OQ6: answered 2026-11-21 (see the answers at the top): no design cap on the side, resource guards only, device capability moved to the viewer (FR-600, FR-607, V1, V3); up to 9,999 factions, viewer palette as follow-up V2, the 8,132-faction stress proof (FR-607, FR-614).
- [NEEDS CLARIFICATION] OQ7. Insets? **A (recommended):** in scope (FR-601), minimal: same scale, a pixel position, no overlap with selected land; needed for the Canary Islands at a useful scale. **B:** out of scope: the Canaries cost 3.6 times the ground per pixel in one frame, or are excluded (as in the dev map).
- [NEEDS CLARIFICATION] OQ8. Projection for the world? **A (recommended):** Lambert azimuthal equal-area (003b) plus Equal Earth with central meridian 0°, both in the square frame the viewer was judged on (a world map then fills about half the square). **B:** Lambert only: no world map. **C:** also non-square images for the world: the id image contract allows them, but the viewer was never judged on one; a later spec.
- [NEEDS CLARIFICATION] OQ9. How is the sea given? **A (recommended):** named seeds (003b) plus sea units from the source (marine regions), with enclosed water joined as 003c. **B:** seeds only: simpler, but a source with sea polygons cannot use them.
- [NEEDS CLARIFICATION] OQ10. Gaps between polygons? **A (recommended):** optional `gapFill` for small enclosed water, off by default so 003b's behaviour is unchanged. **B:** always fill: real lakes and lagoons would become land.
- [NEEDS CLARIFICATION] OQ11. Proof of the generalisation? **A (recommended):** the dev map equivalence test (FR-611) on the committed Natural Earth data, plus a small synthetic sample for what the dev map does not use. **B:** the sample only: the generalisation could drift from 003b unseen.
- [NEEDS CLARIFICATION] OQ12. Several features with one key? **A (recommended):** one unit with several polygons, names must agree (official municipal files ship enclaves as separate records). **B:** `duplicate-unit-key`: forces the author to dissolve the source outside first.
- [NEEDS CLARIFICATION] OQ13. A map title? **A (recommended):** none, as in the first draft: the map id of `MBRG_MAPS` names the map; a title changes the package format (ask first, a spec of its own).
